# v0.9.2

Three server fixes found while running qtask's production workload on v0.9.1: a slow startup on
namespaces with many unique constraints, a slow `ORDER BY … LIMIT` when a BTREE walk is the wrong
plan, and no way to default a missing counter inside an `UPDATE`. There are no format or protocol
changes, and nothing to migrate.

## What changed since v0.9.1

**Opening a namespace with unique constraints is about 10x faster (#319, fixes #316).** At open,
the unique-key registry is rebuilt from every document. It decoded the whole document body once per
constraint field, so qtask's thirteen `_u_*` constraints decoded each document thirteen times,
embeddings included. That was 93% of a ~75 s open at 517k documents. The rebuild now scans each
body's top level once and decodes only the fields a constraint names. A 200k-document namespace of
the same shape now opens in 1.6 s instead of 15.3 s. The remaining time is the storage scan's
block reads, which every full scan pays. A malformed document still fails the rebuild, as before.

**SQL has `COALESCE` and `CASE` (#320, fixes #317).** `SET a = a + ?` on a document without `a`
stores NULL, and there was no way to supply a default. Now:

- `COALESCE(e1, e2, …)` returns the first argument that is neither NULL nor missing.
  `UPDATE … SET attempts = COALESCE(attempts, 0) + 1 … RETURNING _doc` counts from zero on a
  document without the field, atomically.
- `CASE WHEN c THEN r [WHEN …] [ELSE r] END` and the simple form `CASE x WHEN v THEN r … END`
  work in projections, WHERE, ORDER BY and SET. Without ELSE the result is NULL.
- An aggregate inside either is refused with a planning error, because a grouped query would
  evaluate it on the group's first row and silently not aggregate.
- `case` is still usable as a column name. As the operand of a simple CASE it must be qualified
  (`CASE docs.case WHEN …`).
- `SELECT COALESCE(NULL, 1)` works without FROM. A table-less SELECT now refuses only aggregates.

The server evaluates these, so clients need no change to use them.

**`ORDER BY <col> LIMIT k` gives up a bad BTREE walk sooner, and `EXPLAIN` works (#321, fixes
#318).** When a BTREE on `<col>` exists, the query walks it in key order. If the filtered
candidates' keys sort behind most of the namespace (an `updatedAt`-like column), the walk passed
up to `32 × candidates + 65,536` index entries before falling back, about 5x slower than a plain
top-k. The cap is now `4 × candidates + 256`, and documents already read are handed to the top-k
instead of read again. In the benchmark (100k documents, 2,000 candidates) the bad case went from
6.87 ms to 2.48 ms, against 1.48 ms for a plain top-k; the good case is unchanged at 0.07 ms.

`EXPLAIN [ANALYZE] SELECT …` runs the query exactly as a plain SELECT would and returns one row
with `plan`, `rows`, `rows_examined` and `docs_read`. The plan label reports what actually ran,
for example `index:eq(status)+topk(order(updatedAt) abandoned)`. EXPLAIN accepts only SELECT.

**Build tooling (#315).** PR CI now builds the embeddable Go bundle and compiles it standalone, so
the failure that cost v0.9.0 its binaries is caught before a tag.

## Upgrading

From v0.9.0 or v0.9.1: replace the binary or image; the data directory needs nothing. Clients
0.9.0, 0.9.1 and 0.9.2 all work with a v0.9.2 server, and a 0.9.2 client works with any 0.9.x
server. A statement using `COALESCE`, `CASE` or `EXPLAIN` fails to parse on a v0.9.0 or v0.9.1
server, so upgrade servers before deploying code that sends them.

Rolling back to v0.9.1 is safe for data. From v0.8.x: see v0.9.0's notes.
