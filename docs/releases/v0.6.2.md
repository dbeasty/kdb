# v0.6.2

A bug-fix release for one defect family in distributed sync: a transfer that fails part
way leaves commits resident in memory that were never written to the log, and a check
meant to make the operation idempotent — "this node already holds that commit" — then
reads the leftovers as work already done. The retry does nothing and reports success,
over history a restart will not come up with.

The first of these was shipped knowingly in v0.6.1 and listed under its known issues.
The other two were found by looking for the same shape elsewhere, and are the reason
this is a release rather than a patch to one function. All three need a durable-write
failure — a full disk, an unwritable checkpoint directory, a permissions problem — to
happen at all, and all three make such a failure permanent for the life of the process
rather than transient, which is what turns a bad hour into a rebuild.

A fourth fix here is not like the others and needs no failure at all: a snapshot
bootstrap **refused on its merits** — by a unique constraint this node's schema declares
and the sending peer never had to honour — could still leave durable state behind. That
one is reachable by ordinary use between two nodes whose schemas differ.

## Fixes

**A snapshot install that failed part way left the namespace unbootstrappable until the
process restarted.** This is the known issue listed in v0.6.1. `InstallSnapshot` admits
the snapshot's root, moves `main`, then makes the result durable. Either of the last two
can fail, and the undo rolled back storage and `main` but left the root resident in the
DAG with nothing pointing at it. A snapshot bootstrap is refused for any namespace
holding more than its genesis commit, so the orphan refused every later attempt for as
long as the process lived. The node could only be bootstrapped again by restarting it.

**A graft that failed to reach the log reported success on every later attempt.** `Graft`
stores the root's state, records it in the namespace marker, admits the root, then logs
it. If the log write or the fsync behind it failed, the root stayed resident but
unlogged. `Graft` leaves a root it already holds alone — so every later attempt in the
same process short-circuited on the orphan and returned success for a graft that had
never been logged, while a restart came up without the root at all and the marker
already named it. The orphan also counted toward the commit count that decides whether
a namespace is still fresh enough to bootstrap from a snapshot.

**A deepen that failed to reach the log logged nothing on retry, and reported success.**
`Deepen` stores a shallow root's fetched ancestors and then logs them. If that failed
the commits stayed resident with no frame in the log. What to log was taken from the
store loop, which passes over any commit the DAG already holds — so a retry skipped
exactly the commits the failed attempt had left behind, logged only the root,
unshallowed it and reported success over history no restart would rebuild. The history
horizon was collected the same way, so a retry could log a parentless commit the marker
did not name; a replay meeting that commit fails the open outright, for want of parents
no peer has.

**A snapshot bootstrap refused on its merits left durable state behind.** The install
hook wrote the checkpoint first and rebuilt the unique-key registry second. The whole
bootstrap is undone in memory when that hook fails — so a rebuild that refused the
snapshot, because the peer's documents violate a unique constraint this node's schema
declares and the peer never had to honour, left a checkpoint and a namespace marker on
disk describing a bootstrap that no longer existed anywhere. That namespace then looks
fresh, accepts local writes on genesis, and reopens from a checkpoint its log does not
descend from. The rebuild now runs first, so nothing durable is written until everything
that can still refuse the snapshot has agreed to it; and a failure to write the
checkpoint resets the registry, which otherwise kept refusing later local writes as
duplicates of documents the node no longer held.

Unlike the three above, this one needs no injected failure and no full disk — two nodes
whose schemas differ on a unique constraint are enough.

## How they were fixed

The three are not one fix, because the operations are not alike.

`InstallSnapshot` and `Graft` each admit a single commit without its parents, and both
undo it with a new `dag.DropShallowCommit` — deliberately narrow rather than a general
commit delete. It refuses a commit that is not a shallow root, one that is pinned or
named by a branch head or tag, and one with a resident child, whose history removing it
would truncate rather than undo. A failure to take the root back is reported rather
than swallowed: a retry that will be refused is worse than a loud failure.

`Deepen` stores a chain, mostly through the ordinary commit path, so there is nothing
narrow to take back and the DAG should not grow a general delete for this. Writing the
log before the DAG is not an option either — a checkpoint pairs a snapshot of the DAG
with the log position it has been replayed through, so one taken between the two would
record a DAG missing commits the log had already passed, and the next open would skip
their frames for good. `Deepen` is made genuinely re-runnable instead: what must be in
the log, and which commits the marker must name as horizons, are read back out of the
DAG rather than remembered from the store loop. A repeated frame costs log space and
nothing else, because replay stores a commit only when the DAG does not already hold it.

## Upgrade notes

No on-disk format change, and no action needed on upgrade. Nothing about how a
namespace is written or read differs from v0.6.1; only the failure paths changed.

## Known issues

The snapshot-install issue listed under v0.6.1's known issues is fixed by this release.

**The embeddable Go source bundle does not include `kdb/server`.** A downstream project
that vendors the bundle and imports `kdb/server` directly to build its own server image
gets a zip without it. The bundle covers the in-process embedding surface only. This is
unchanged from v0.6.1 and earlier.
