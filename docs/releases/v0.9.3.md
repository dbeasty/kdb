# v0.9.3

Closing qtask's gap to MongoDB: less CPU per request, a cache pool sized from the machine, composite
indexes, single-statement `$unset` and upsert, queue claims that scale past one at a time, and a
TypeScript client that keeps several writes in flight. There is no data migration, but **a store
that has a composite index cannot be opened by v0.9.2**: read "Upgrading" before rolling out.

## Performance

qtask's Docker benchmark (prod scale, 517k documents, each database alone in 2 CPUs / 4 GiB, MongoDB
`j:true` in the same run), actions/s at 1 / 8 / 32 users.

Mixed, read and write: v0.9.2 and the server after #333/#334, in the same run on the same data
(2026-10-22). On identical data the release build matches that server in mixed (A/B, 2026-10-23);
the later changes are about claims.

| profile | v0.9.2 | v0.9.3, default | v0.9.3, `--document-copies` | MongoDB |
|---|---:|---:|---:|---:|
| mixed | 30 / 68 / 48 | 50 / 121 / 122 | 68 / 191 / 202 | 149 / 458 / 522 |
| read-heavy | 28 / 62 / 39 | 46 / 110 / 108 | 68 / 187 / 187 | 161 / 366 / 408 |
| write-heavy | 34 / 95 / 98 | 55 / 176 / 189 | 67 / 230 / 262 | 159 / 638 / 804 |

The queue claim (claim a job, complete it, re-enqueue it) gained most in the later changes, each
measured against the server before it in the same run. In the release run (2026-10-23) it does
**272 / 754 / 751 claims/s, against 254 / 2,146 / 2,642 on MongoDB**; on 2026-10-22, on the older
dataset, v0.9.2 did 107 / 298 / 319. No errors in any cell.

On a store loaded fresh by `migrate:kdb backfill` (the release run, 2026-10-23), mixed at 8 users
is 88-99 actions/s: about a quarter below the table, for any server version. A bulk import writes
large commits, and with `--document-copies` off a read decompresses its document's whole commit. A
store that has been running since its import, or one switched to `--document-copies`, does not pay
this.

## What changed since v0.9.2

### Server

- **CRC32 in hardware** (`hash/crc32`, #333). The byte-at-a-time loop was 16% of CPU. The output is
  bit-identical.
- **The cache pool is sized from the machine** (#333): an eighth of the cgroup memory limit, or of
  RAM, between 64 MiB and 4 GiB. It used to be a fixed 64 MiB. `--cache-mb` sets it explicitly.
  Embedded runtimes keep 64 MiB. **A server's resident memory grows accordingly.**
- **`--document-copies`** (#333, off by default, `KDB_DOCUMENT_COPIES`). Documents in bulk commits
  get a copy of their own, so a read does not decompress the whole commit: +52% mixed throughput for
  about +59% disk. It can be switched on restart in either direction. Turning it on re-files
  existing documents in the background; turning it off ends with a major compaction that gives the
  disk back (517k documents: 22 s on, 19 s off).
- **SELECTs on a non-SNAPSHOT session no longer queue behind each other** (#333).
- **Composite BTREE indexes** (#334): `CREATE INDEX i ON t (a, b, c) USING BTREE`. `WHERE a = 'x' AND
  b = 'y' ORDER BY c [ASC|DESC] LIMIT k` walks the index like a Cassandra clustering key and reads
  about k documents, and a queue claim (`UPDATE … ORDER BY c LIMIT 1 RETURNING`) reads one job instead
  of every pending one. The walk is used only where it provably returns every matching row in SQL's
  order; otherwise the existing paths answer. A composite BTREE cannot be UNIQUE: declare
  `UNIQUE (a, b)` on the table.
- **Index history fits a budget** (#334). All of a namespace's indexes keep their as-of history
  within 5% of the cache pool together, as one window of commits: qtask's 51 indexes held about
  330 MB outside the pool, now about 45 MB. Reads at a commit past the window fall back to the
  documents, as before.
- **Queue claims stay on the index walk under contention** (#335): a candidate search that the
  index could not serve exactly is retried at a newer head, and keys left empty by claims are
  compacted away instead of slowing every later walk.
- **`UPDATE … REMOVE a, b.c`** (#336) takes fields out of documents, as MongoDB's `$unset` and
  DynamoDB's `REMOVE` do. `SET x = NULL` still stores a null. A missing path is left alone, and
  attachments are kept.
- **`INSERT … ON CONFLICT (cols) DO UPDATE SET … [REMOVE …] [WHERE …] | DO NOTHING [RETURNING …]`**
  (#338): an upsert on a declared unique constraint in one statement, decided under the write gate,
  so concurrent upserts of one key never insert twice and never fail with a unique violation. It
  takes one `VALUES` row and may name its document's `kdb_id`, which must be new. The reply's
  generated ids name the document only when the row was inserted. A plain, buffered `INSERT` may not
  name `kdb_id`.
- **Immediate writes no longer hold the write gate longer as concurrency grows** (#339):
  - an `UPDATE` whose WHERE names its documents by `kdb_id` is decided among those documents alone;
  - which documents changed between two commits comes from a record of what each commit wrote,
    instead of a diff of the two document trees;
  - per-commit index bookkeeping runs after the gate is released.

  Claims at 32 workers: +45%, together with the client's session pool below and qtask running
  its immediate writes side by side.

### Clients

- **TypeScript: a pool of write sessions per namespace** (#337, `sessionsPerNamespace`, default 8;
  1 keeps the old single session). Self-contained writes (an `exec` and its auto-commit, a commit
  carrying its own transaction) each take a session of their own, so one process keeps several in
  flight. Leases, queries and transaction control stay on the namespace's own session, and while the
  client holds a lease in a namespace every write there does too.
- **TypeScript: no zstd replies on a loopback connection** (#333, `ConnectOptions.compression`,
  default `"auto"`). Reply compression was 20% of server CPU. The Go and Kotlin clients still
  request it.

### Docs

- Unqualified SQL tables route to a matching sibling namespace (#323).
- npm trusted publishing is set up, and the client's `repository` field is added (#324). This is
  the first release whose npm package is published by the release workflow.

## Upgrading

From v0.9.0, v0.9.1 or v0.9.2: replace the binary or image; the data directory needs nothing.
The 0.9.2 and 0.9.3 clients both work with a v0.9.3 server, and the 0.9.3 client works with a
v0.9.2 server (qtask's conformance suite passes in each pairing); the handshake accepts any 0.9.x
pairing. A statement using `REMOVE` or `ON CONFLICT`
fails to parse on an older server, so upgrade servers before deploying code that sends them; qtask
detects that and falls back.

The cache pool now defaults to an eighth of the memory limit (at most 4 GiB). Set `--cache-mb` to
keep a smaller footprint.

**Rolling back to v0.9.2 is safe for data, but v0.9.2 refuses to open a namespace that has a
composite index** (`opening indexes: a BTREE index on _c already exists`). Before rolling back,
drop every composite index on v0.9.3 (`DROP INDEX <name> ON <table>`), stop the server, then start
v0.9.2. Tried on qtask's data: v0.9.2 then opens it, did not keep the composite indexes when qtask
declared them again, and served qtask without them. From v0.8.x: see v0.9.0's notes.
