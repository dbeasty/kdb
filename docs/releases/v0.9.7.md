# v0.9.7

**The server code is identical to v0.9.5 and v0.9.6.** Both published their container image
(linux/amd64 and linux/arm64) and the `@limidus/kdb-client` tarball, but not their binaries, jars
or Go source bundle: the release job runs the embeddable bundle's full test suite on a small
runner, and `TestGraphResidentTierLongRun` failed there each time. Its unpaced writer committed
~170k commits/s, several times what a server does, and outran the graph flusher on 1-2 CPUs
(peak 145-300 MiB against a ~68 MiB bound; v0.9.6's 1 ms pause, #360, was not enough). It now
paces its writer at 50k commits/s (#362; peak 24 MiB at 1 and 2 CPUs). #360 also fixed
`TestLargeFrameIsDecompressedOnceForAllItsDocuments`, which assumed the read path, not the
open-time re-filing pass, files the bodies. Test assumptions, not server defects; this release
republishes the same code with every artifact. Everything below is v0.9.5's notes.

A performance release: the write path no longer serializes on the commit gate, kdb-service on
Linux syncs with `fdatasync` into preallocated segments, and the commit graph flushes by size so a
100k-document store holds about 30% less memory. There is no data migration and no on-disk or wire
format change; v0.9.4 opens a store written by v0.9.7 and the reverse (checked, including after
`kill -9`).

## What changed since v0.9.4

### Performance (#345-#357)

Per-PR A/Bs and the whole-release comparison below. The plan, every measurement and the traps are
in `docs/kdb-basic-rw-performance-plan.md`.

- **The write path works off the gate** (#345, #348, #351, #357). An Upsert's merge and hash are
  worked out before the gate (W2, W3), each commit is encoded once (W5), a document's JSON is
  validated with a scan rather than a map (W6), a write takes one trie walk under the gate (W7),
  a full memtable is written on its own goroutine (W4), commits that leave the same tree each file
  their own locations (F1). An Upsert builds on the Upsert queued ahead of it and a stale premerge
  is redone off the gate once (W9: stale premerges on update@32 17.7% to 0.9%;
  `kdb_upsert_premerge_total{outcome}` on `/metrics`).
- **kdb-service on Linux defaults to `fdatasync` into preallocated segments** (#345, D1) and the
  next segment is prepared ahead of need, with background writers trickle-synced (#346, D2).
  Durable writes are 1.5-2x v0.9.4 and the worst write latency drops from over a second to tens of
  milliseconds.
- **Reads** (#349, #350): superseded versions leave the body cache first (R1) and a cold read never
  rescans the open segment (R2). Read95 mixes are 1.1-1.3x in the durable runs; point reads are
  unchanged (the control).
- **Memory** (#356, M1): the commit graph flushes by size, merges size-tiered and carries a bloom
  filter. Container memory after the 100k-document matrix: 1,292 MiB to 906 MiB.
- **Embedded cache default** (#354, E2): see Behaviour changes.

### Fixes

- **Silent lost update on concurrent Upserts** (W1, #345). An Upsert resolved the head before
  queueing for the gate and merged onto that version, so a writer queued behind another wrote back
  a body without the fields the writer ahead had just set; LAST_WRITE reports no conflict, so
  nothing said so (16 concurrent Upserts to one document kept 2 of 16 fields). The merge now reads
  the live head at the gate front.

### Features

- **`kdb/docdb`** (#352, E1): a concurrent document API for embedders.
- **`--coalesce-writes`** (#355, W8; off by default): several writes per commit. update@32 fast:
  1.16x on a zipf key choice, 1.69x on 16 hot documents.

### Behaviour changes to know about

- **Disk per namespace (Linux kdb-service).** `--sync-mode` now defaults to `fast` and
  `--preallocate-segments` (also `KDB_PREALLOCATE_SEGMENTS`, `preallocateSegments`) to on, so each
  open namespace's active segment takes 64 MiB of disk up front. The durability guarantee is
  unchanged (`fdatasync` flushes the data and the metadata needed to read it back through the drive
  cache like `fsync`). To restore v0.9.4's behaviour: `--sync-mode full --preallocate-segments=false`.
  macOS, Windows and embedded runtimes keep their previous defaults.
- **Embedded cache default.** An embedded store with no `MemoryBudgetBytes` now gets a sixteenth of
  the memory the process may use (cgroup limit, else physical RAM), at least 64 MiB and at most
  256 MiB (was a fixed 64 MiB), shared by every default-sized store in the process. Set
  `MemoryBudgetBytes` to pin it. Android and iOS stay at 64 MiB.

and without `kill -9`, works.

## Upgrading

Replace the binary or image. On Linux, budget 64 MiB of disk per open namespace (see above).

Rolling back to v0.9.4 is safe: it reads preallocated segments and the new commit-graph layout.
