# v0.7.1

**There was no v0.7.0 release.** `VERSION` read 0.7.0 on `main` for most of this cycle, but no
v0.7.0 tag, binary, image or package was ever published. v0.7.1 is the first 0.7 release, and these
notes cover everything since v0.6.2.

This release is mostly about **multi-node correctness**. A new end-to-end suite runs real
clusters of `kdb-service` processes — several nodes, concurrent writers on every one,
`kill -9`, drains, partitions, late joiners — and checks that every node ends on the same head
commit with the same documents. On v0.6.2 it found three ways for a cluster to get stuck or
stop converging, each silent, each fixed here. It also carries a SQL correctness fix whose
behaviour change existing clients must know about, and crash recovery that opens about 400
times faster.

It also closes two ways the delta log could silently lose acknowledged commits — damage in the
middle of a segment was read as the end of it — and a compaction race that could make a stored
blob read as missing. Resolution chains gain an opt-in version 2 that fixes three ways a chain
could converge on the wrong value — one of them silently dropping `field-merge` writes.

It also brings the client and operations work for moving an application onto KDB: a replace
write, paging, indexes that stay fast on schemaless namespaces, `COUNT(*)` without a scan, and
much better disk-mode loading and restart at a million documents. It adds two new TypeScript
packages (`@kdb/codegen`, `@kdb/embed`), and the Go engine now runs on Windows (preliminary).

It is **0.7, not v0.6.3**, because of the behaviour changes below.

## Behaviour changes — read before upgrading

**A query whose result exceeds the result bound now fails instead of being silently
truncated (#115).** v0.6.2 collected the first 10,000 document ids and *then* applied the
`WHERE` clause, so on a namespace with more documents `SELECT COUNT(*)` said 10000, a filter
matching only later documents returned nothing, and `UPDATE`/`DELETE` by id could report
success while changing nothing. Results are now exact, and a result larger than the bound fails
with `RESOURCE_EXHAUSTED` — a non-retryable error in every client — rather than handing back a
prefix the caller cannot tell is incomplete. The bound is `--max-result-rows` /
`KDB_MAX_RESULT_ROWS` / `maxResultRows` (default 10000, restart to change; it also feeds the
admission cost model's memory estimate). `kdb_id = ?` and `kdb_id IN (...)` are now served by
key, so updates and deletes by id no longer scan the namespace. The TypeScript client gains
`delete()` and `Transaction.deletes`. Kotlin has the same semantics
(`SqlResultLimitException`, `KdbErrorCode.RESOURCE_EXHAUSTED`).

**`CREATE UNIQUE INDEX` now enforces uniqueness on a schemaless namespace (#147).** It used to succeed
and then allow duplicates, including concurrent ones: uniqueness is enforced at commit from the
namespace schema's constraints, and an index took no part. The statement now installs the
constraint. On a schemaless namespace that is a *constraints-only schema* (unique tuples, no
declared fields): the namespace keeps answering queries about undeclared columns, the constraint
is checked against the data already there (a violation refuses the statement and leaves nothing
behind), recorded so it survives a restart, and replicated. Documents that omit the field claim
nothing. `CREATE UNIQUE INDEX name ON t (a, b)` is a compound constraint with no lookup
structure. On a namespace that declares its fields the constraint must already be declared in the
schema (`CREATE TABLE ... UNIQUE`); otherwise the statement fails with a message saying so. A
definition an earlier version stored still loads, but carried no constraint: create the index
again to get one. The Go server only; the Kotlin engine refuses `HASH`/`BTREE` indexes on
undeclared fields, so it cannot be asked for this.

**A node may now move `main` to a commit that is not a descendant of its previous head
(#114).** When two heads hold identical content, a node no longer stacks another pairwise merge
on top; it builds one canonical "join" whose parents are the content-carrying commits
underneath, so every node holding the same commits builds the identical head. Only empty merge
commits ever drop off `main`'s path; documents are never touched, and startup replay accepts a
logged join that supersedes the head. Anything outside KDB that assumed `main` only moves to
descendants — an external tool walking first parents — should read `docs/kdb-distributed-plan.md`.

**`kdb branch checkout` is refused (#117).** It used to set a branch to the head it already had
and print "checked out" while changing nothing; the CLI keeps no current branch. Read another
branch as the revision `branch:<name>`.

**A damaged delta-log segment now stops startup (#121, #129)** with an error naming the segment
and byte offset, instead of being skipped or read as ending at the damage — either of which could
silently open a node behind its last acknowledged write. A torn tail left by a crash still
recovers as before. Recover a damaged namespace with `kdb-inspect verify`, then
`repair-segments` or a restore.

**Resolution chains have a version 2, opt-in, with corrected merge semantics (#134).** A chain
set with `"version": 2` (`PUT /v1/ns/{ns}/resolution`) merges against the true merge base, settles
`field-merge` collisions per field, and holds a `validity` conflict until the node has the schema
(see Fixes — resolution chains). A chain without a version, or with `"version": 1`, behaves and
hashes exactly as in v0.6.2. Switch a namespace's chain to version 2 only after **every** node runs
this release — see Upgrading. `GET …/resolution` now also reports `version`, `supported` and
`advertisedHash`.

**A backup refuses a segment damaged in place (#131).** `kdb-inspect backup` exits 1 and
`POST /v1/ns/{ns}/backups` answers 409 `segment_damaged`, naming the segment, the byte offset and
the next intact frame, and nothing partial is uploaded or recorded. Before, a backup silently kept
only the part of the segment before the damage — and an incremental backup over a newly damaged
segment overwrote the shared object its base backup names, corrupting the base. A crash's torn
tail still backs up as before. Repair or restore the source (`kdb-inspect verify`, then
`repair-segments` or a restore), then back up again.

**The peer-sync and stream listeners are off by default (#145).** `--peer-addr` and
`--stream-addr` used to bind `127.0.0.1:9091` and `:9092` when not given. Now only the SQL listener
is on by default, so two default instances can run on one host. **A node that relied on the old
default stops serving peer sync after the upgrade**, and the peers pulling from it stop
converging. Before upgrading such a node, set its peer address explicitly, for example
`--peer-addr tcp://127.0.0.1:9091?bind=true` (or `KDB_PEER_ADDR`, or the config file), and do
the same for `--stream-addr` if anything subscribes to it.

**`replaceIf`, `replaceIfPresent` and `compareAndSwap` replace the document (#145).** They used to
merge the new fields into the old document. They now use the new replace write (see New), so a
field missing from the new value is gone afterwards. The server arbitrates the race: with two
processes racing on one content hash, exactly one wins.

**Go `Client.Exec` returns `(int, error)` (#145).** The int is the number of rows the statement
affected. The TypeScript `exec` resolves to the same count. Concurrent DML through one client no
longer fails with `no pending transaction to commit`: `exec` holds a per-namespace lock across
the statement and its auto-commit.

**`@kdb/client` is published at the server's version and checks it (#145).** The handshake
carries `serverVersion`, and `connect` refuses a server outside the client's release line (same
major; while the major is 0, same minor). It also refuses a server that reports no version: any
release before this one, or the JVM engine. Pin `@kdb/client` to the server release you deploy,
or pass `skipVersionCheck: true` deliberately.

**Kotlin/JS and Kotlin/Native read and write real zstd (#116, #109).** They used to label
uncompressed blocks as zstd, which Go and the JVM could not read. A Kotlin/Native data directory
written before #109 is refused (no Native build was ever released).

## New

**Writes and queries (#145).**
- **Replace write:** `replace=true` on a write op (Go and TypeScript clients, the Kotlin engine)
  replaces the whole document in one op and one commit, with no window between a delete and a
  write. It is an additive wire field and is never stored, so replay, history and peer sync see
  no new kind of op.
- **Paging:** a result larger than `--max-result-rows` can be read in pages with
  `pageSize`/`continuation` on `sqlExec`, `QueryRawPages` in Go, and `queryRawPages`/`queryAll`
  in TypeScript.
- **Indexes on schemaless namespaces stay fast.** A JSON-path index used to replay its whole
  event log on the first read after every write. It now updates incrementally, and the planner
  uses the most selective conjunct it can serve. Filtered reads stay at tens of microseconds from
  1k to 100k documents.
- **`COUNT(*)` without reading documents:** it is answered from the tree size or an index count,
  except when that is not provably equal to reading. Other aggregates still read documents.
- **Keyed `kdb_id` lookup and an examined-rows budget in the Kotlin engine**, matching Go.

**Disk-mode performance (#145, #153).** A new disk-mode benchmark (`scripts/bench-disk.sh`,
`docs/benchmarks/disk-mode.md`) found two defects, both fixed:
- At 1M documents, a bulk load took 955 s; it now takes 19.8 s. Document-cache eviction had
  scanned pinned entries.
- The first scan after a restart took 26.6 min; it now takes 21 s. The scan had decoded a whole
  commit frame once per document.

Read handles are cached instead of opened per read. A small namespace's scan no longer
allocates a full 1.5 MiB scan window (#153). Memory at 1M documents went down:
- RSS after loading: from 1,285 MB to 723 MB.
- RSS after a restart and a full scan: from 2,236 MB to 1,289 MB.

Above 256 MiB of live heap, the Go collector is now paced to the live heap
(`--gc-headroom-percent`, default 25).

**Operations (#145).**
- `kdb_namespace_documents` and `kdb_namespace_commits` on `/metrics`, document counts on
  `/healthz`, and alert rules in the user guide.
- A backup/restore drill (`scripts/backup-restore-drill.sh`) that CI runs.
- Namespaces opened on demand get the maintenance loop.
- Expiry is documented (a document is hidden, not deleted), with a restart test.

**TypeScript packages (#144).**
- **`@kdb/codegen`** generates TypeScript types, column metadata and DDL from a schema's JSON form,
  plus a typed SQL builder. `kdb-codegen --check` is a CI drift gate.
- **`@kdb/embed`** is the Go engine compiled to WebAssembly, behind the same operations as
  `@kdb/client`. It runs in memory or durably on IndexedDB (`openEmbedded({ persist: { name } })`).
  It has no peer sync, and a `CREATE TABLE` schema must be re-applied on reopen
  (`Table.ensure()`).

Both packages are versioned 0.1.0 and are not yet published by the release workflow.

**Windows, preliminary (#151, #156).** The Go engine gets the runtime pieces Windows needs, beyond
cross-compiling for it:
- Directory fsync and renames use Windows-safe paths.
- Open files can be renamed and deleted.
- Transient sharing violations are retried.
- The data-directory lock uses `LockFileEx`.
- Free space, memory and volume identity work.
- Reserved device names are refused as namespace ids.

CI runs the Go suite on `windows-latest`, and it passes (#156). Three Windows bugs were fixed to
get there:
- Writing the node identity and starting a cross-namespace transaction no longer fail with
  `Access is denied`. The files were being fsynced through a read-only handle.
- Promoting a namespace now works. A file handle left open inside the namespace directory blocked
  its rename.
- A `kdb://file` URL with a drive letter (`file://C:\kdb\...`) keeps its drive. It used to become
  the drive-relative `C:kdb`.

Windows support is new and has not been run in production. Treat it as preliminary.

## Fixes — distributed sync

**The `deepen=true` peer option now rescues a snapshot joiner stuck behind its root (#128).** The
`ShallowBoundaryError` such a joiner reports names `deepen=true` as a cure, but the replicator
skipped deepen for any namespace whose sync had just failed, which that error always is. It now
deepens after that error, and only that one; other failures still skip it. Found by the
mixed-version upgrade test (#125), whose test of it now passes against a v0.6.2 server.

**A five-node mesh could fall into a merge storm and never converge (#114).** Nodes holding
identical documents kept creating empty merge commits faster than they spread: over 10,000
after writes had stopped, with every sync succeeding and no node ever settling. Needed three or
more nodes and slow syncs (a loaded machine). See the `main` behaviour change above.

**A node that had drained during replication came back permanently broken (#113).** A clean
shutdown could checkpoint a peer commit the node had received but not yet logged; after restart
every sync from or to that node failed with `commit ... has no frame in the delta log`. Seen in
about half of drain-under-load runs. Checkpoints now describe only logged commits, shutdown
stops inbound peer sync first, and **a data directory already in this state heals** on the next
sync, from the peer's copy of the commit.

**A snapshot-bootstrapped node got stuck forever once the cluster committed on a branch forked
behind its snapshot (#111).** Every sync failed with `storing commit ...: missing parent ...`.
The joiner now fetches just that fork point's state — one transfer per fork point, never the
history — and a node that cannot is told so with a typed error that names `deepen`. The serving
node must have this fix (see Upgrading).

**A snapshot-bootstrapped node that is only ever pushed to now takes branches forked behind its
snapshot root (#140).** Before, a hub whose peers push to it (`mode=push`), or a node with no
`--peer` of its own, refused such a push with "missing parent" on every sync, for ever. Now the
pushing node sends the fork point's state on the same connection. Pushers from v0.6.2 can't: their
push fails with a `SHALLOW_BOUNDARY` error naming the commit and its missing parent. Upgrade the
pushing nodes, or have the hub pull from a peer once or deepen (`POST /v1/ns/{ns}/deepen`).

**The ops loader indexed the delta log once and never again (#113)**, so a commit logged after
its first cold load and later evicted from memory reported "no frame in the delta log" though
its frame was on disk. Needed only a small enough memory budget.

## Fixes — durability and recovery

**Crash recovery opens about 400 times faster (#123).** Every replayed commit probed the blob
store, and each probe rebuilt the SSTable reader and read the whole table just to learn its
size: 14,000 commits with no checkpoint took 149 s to open, now 0.36 s. Replay after a crash
covers everything since the last checkpoint (up to the maintenance interval, 5 minutes by
default), so a busy node could take minutes to come back.

**A table flushed during a compaction disappeared until the next restart (#123).** Compaction
replaced the whole table list with its output, dropping tables added while it ran.

**Damage in the middle of a delta-log segment silently dropped every commit after it (#129).**
Every scanner ended a segment at its first garbled header or CRC mismatch, which is right for a
crash's torn tail and wrong for damage: a node opened at commit 3 of 6, or 5 of 8, with no error.
The rule now is that a torn tail is only bytes at the very end of a segment with nothing intact
after them — appends are sequential, so an unfinished write cannot be followed by a finished one.
Damage with intact frames after it is refused (`DamagedSegmentError`), in Go and Kotlin; a
checkpoint that already holds the damaged segment's commits still opens without loss.
`kdb-inspect verify` reports it as `mid_log_corruption` (it used to say `torn_tail`), and
`repair-segments` refuses to truncate acknowledged commits after the damage (it used to delete
them). A frame header torn right after its magic — what a crash can leave in a preallocated
segment — no longer makes the namespace unopenable.

**Backups taken before this release may be missing commits, and `backup-verify` cannot tell
(#131).** A backup made from a segment damaged in place held only the commits before the damage,
and `backup-verify` reports it clean because it re-hashes what was uploaded. If a node's data
directory may have suffered disk damage, run `kdb-inspect verify` against the source directory
before relying on its older backups; a restore of such a backup either fails to open (damage in an
older segment) or opens behind its last acknowledged commit (damage in the newest one).

**A lookup racing a compaction could miss a stored key (#127).** A read that took the table list
just before a compaction's swap could find its table deleted under it and report not found;
under `history=none`, or with bodies held outside the log, that surfaced as a missing document
or a silently skipped row. Tables are now reference-counted, so compaction deletes an input only
after its last reader is done.

**Replayed commits that are stored but not applied are counted and logged (#121)**, and exposed
as `recovery` in `GET /v1/ns/{ns}/status`. A single-writer log reports zero.

**Issue #43** (an acknowledged write reported lost after `kill -9`): a new reproducer kills the
real server 620 times across five durability configurations without losing any of 110,950
acknowledged writes, and runs nightly on Linux (#122). The old e2e test reported any failed read
as a lost write; it now tells missing, rolled-back and unreadable documents apart (#112). #43
stays open until the Linux soak has run.

**A later backup can no longer change an earlier one (#136).** Sealed delta segments are now stored
under a key that includes a hash of their contents, so a segment changed by `kdb-inspect
repair-segments`, a repair record or a truncation gets a new object and the base backup keeps the
exact bytes it recorded. This also stops an **S3 replica mirror that shares the backup's bucket and
prefix** from overwriting or deleting backup objects — it wrote to exactly the old backup keys.
Backups made by earlier versions still verify, restore and serve as incremental bases, and
`backup-verify` now names the later backup that overwrote an older backup's shared object. If you
ran replication and backups against the same S3 bucket and prefix, run `kdb-inspect backup-verify`
on your existing backups.

**A failed log write during a peer sync could leave a node that restarts broken (#137).** If the
delta log write failed while a node was deepening history, merging a peer's changes or
fast-forwarding to them, the node could restart failing every sync with "has no frame in the delta
log", lose the merge, or refuse to open. Such a failure now leaves the node as a crash would: the
next start is clean and the next sync fetches what was lost. On shutdown, peer sync served over
WebSocket (`--peer-http`, `/kdb/sync`) is now ended and waited for before storage closes, as the TCP
peer listener's already was.

## Fixes — SQL, storage, clients

- **SQL silently truncated results at 10,000 documents (#115)** — see Behaviour changes.
- **A vector query with no `LIMIT`, or a huge `k`, sized its allocations by `k` (#145)** — about
  148 GB at k=10⁹. `k` and `ef` are clamped to the index size, in Go and Kotlin.
- **A unique value held by the nil-UUID document was treated as released (#147).**
- **Go `json` path accessors panicked instead of returning an error (#107)**, including a path
  reachable from SQL `UPDATE ... SET` on a JSON path with an out-of-range or negative index.
- **Kotlin's WAL ignored its configured segment size (#119)**; `StorageEngineConfig.walMaxSegmentBytes`
  now takes effect (default 64 MiB).
- **Kotlin TCP and WebSocket servers leaked exceptions on stop (#110)**, the WebSocket server on
  every stop, and cancelling a WebSocket `listen` never closed its listening socket. `stop()` now
  waits for its connection handlers.
- **`@kdb/codegen`'s `execute()` and `Table.create()` failed to typecheck** against the new
  `exec` row count (#150).
- **The in-memory stream transport dropped frames, and the stream subscriber could drop a desync
  error (#120)**, after which a subscriber never learned its state was wrong. A full event buffer
  now ends the subscription with an error the consumer sees.
## Fixes — embeddable Go bundle

**The embeddable Go source bundle now includes `kdb/server` (#108).** This is the known issue
listed in v0.6.2. A downstream project that vendors the bundle and imports `kdb/server`
directly — to build its own server binary or image around the native engine — got a zip
without it, because the bundle's entry points covered the in-process embedding surface
only. `kdb/server` is now an entry point, and the bundle carries its closure: the wire
protocol, the TCP and WebSocket transports, peer sync, streams, stored procedures
(`kdb/script`) and the full-text and vector index packages it reaches. The bundle grows
from 27 to 40 packages.

**Dependency change for bundle consumers.** The bundle's `go.mod` now requires
`github.com/dop251/goja` (the JavaScript engine behind stored procedures) and
`golang.org/x/sync`, plus their indirects (`dlclark/regexp2/v2`, `go-sourcemap/sourcemap`,
`google/pprof`, `golang.org/x/text`). All are pure Go; the bundle still builds with
`CGO_ENABLED=0` on every release platform. A consumer that imports only the in-process
packages compiles none of this in, but the requirements are in the bundle's module graph.

## Fixes — resolution chains

These three only take effect under a version 2 chain (#134); a version 1 chain keeps v0.6.2's
behaviour, including these defects. All were found by a new resolution-chain convergence suite on
3- and 5-node meshes (#130), and every node always converged — the defects are in *which* value.

**`field-merge` could silently drop acknowledged field writes (F1).** A merge took the first common
ancestor found breadth-first, not the nearest — and in a criss-cross there can be several nearest.
Against a stale base a field looked changed on both sides, fell through to whole-document
`last-write`, and the losing side's field writes were lost, under ordinary concurrent load. Version
2 uses every nearest common ancestor, folded recursively into one virtual base when there are
several, identically on every node.

**`field-merge` then `last-write` picked different winners in different merge orders (F2).**
Combined values took the merge commit's timestamp. Version 2 settles each field changed on both
sides by that field's own latest write, which is the same in any merge order.

**A `validity` rule could keep an invalid value (F4)** when a node merged before the schema reached
it. Under version 2 the schema is part of the chain's compatibility hash, and a node without it
holds the conflict until the schema arrives.

**A version 2 chain could stall a node for minutes under a busy mesh (#143).** Building the
virtual base for a merge re-derived the same sets of common ancestors once for every path that
reached them, running the chain's rules at each step, so the work grew exponentially with the
depth of the history. It ran while the merge held the node's write gate, so on a five-node mesh
merging constantly, one node stopped taking writes and peer syncs and never caught up. The nightly
e2e found it on Linux (`test_load_procedure_per_node_counter`, 5 nodes); it did not show on macOS.
The work is now shared, and grows with the history, not exponentially. The result is the same
virtual base on every node, so nothing changes about which value wins. This is in the chain
version 2 code introduced in this release: it affects nobody running version 1 chains, and no
earlier release.

## Fixes — procedures

**A procedure used as a conflict resolver must merge states, and the docs now say so.** The user
guide suggested "add the two counters together", and a procedure computing `local + remote - base`
cannot be correct: a merge never offers a document both sides hold with the same value, `base` is
one common ancestor and can be stale, and the procedure runs again on every node over earlier merge
results. In testing, two +1s converged on 1 and 603 increments on five nodes on about 6×10³⁰. The
user guide ("What a merge-time procedure can rely on") and spec §12.4.1 now state what a procedure
receives and when it runs, require a deterministic function that is commutative, associative and
idempotent, and replace the example with a per-node counter (`{counts: {<node>: n}}`, merged by
per-key max, total summed on read), plus set union and max/min. A version 2 chain gives a procedure
the true merge base, which makes even a summing procedure count correctly in the criss-cross tested,
but it still is not offered documents whose values are equal, so it remains the wrong pattern:
rewrite it as a per-node counter.

## Upgrading

**Upgrade one node at a time.** Stop a node (cleanly, or after a crash), start the new binary on
the same data directory and addresses, and move on. Old and new nodes replicate with each other
throughout. The one flag to check first: a node that never set `--peer-addr` (or `--stream-addr`)
was serving on the old default port and will not after the upgrade. Set it explicitly (see
Behaviour changes). A nightly test does exactly this from v0.6.2 — a
3-node rolling upgrade under writes, a node killed with `kill -9` and restarted on the new
binary, and a 5-node mesh of old and new nodes under writes and kills — and every acknowledged
write survives and every node converges (#125).

**A new node joining by snapshot through a v0.6.2 peer can stop with an error naming deepen.**
Folding a fork point's state needs the serving node to have #111; an older server can't, so the
joiner reports a typed `ShallowBoundaryError` instead of converging. Recover it with
`POST /v1/ns/{ns}/deepen` or `kdb deepen`, or bootstrap with `bootstrap=snapshot,deepen=true`
from the start, or set `deepen=true` on the stuck joiner's peer. Upgrading the serving peers
first avoids it.

**Switch resolution chains to version 2 last, after every node is upgraded.** v0.6.2 ignores the
`version` field and keeps advertising the version 1 hash, so it never merges with a version 2 node;
two v0.6.2 nodes still merge with each other under the old semantics. A node that receives a chain
version it does not support holds every conflict with that reason rather than merging differently.
Once the whole cluster runs this release, `PUT /v1/ns/{ns}/resolution` with `"version": 2` and the
same rules; the nightly upgrade test does exactly this (#134).

**Rolling back to v0.6.2 is only safe from a clean stop.** v0.6.2 does not understand the
canonical join commits this release writes (#114). If a node running this release crashed, do
not start v0.6.2 on its data directory: v0.6.2's replay silently rolls back acknowledged writes,
and upgrading again afterwards does not bring them back (its checkpoint names the old head). Start
the node on this release first, let it recover, stop it cleanly, and only then downgrade.

## Known issues

- **A resolution chain with a `procedure` rule holds a divergence of more than 10,000 conflicting
  documents for ever.** The per-sync budget for procedure calls is 10,000, a larger divergence
  exceeds it on every node and every retry, and the conflict stays held. Settle it through the
  control plane (`POST /v1/ns/{ns}/conflicts/{id}/resolve`) or avoid procedure chains on namespaces
  that can diverge that far. Merge-time procedures also run while the node's write lock is held,
  so a large merge delays local writes for its duration.
- **`MemoryGuard` counts reclaimable page cache as used memory in Linux containers.** It reads
  the cgroup's raw `memory.current`, so a container with a warm page cache can report `critical`
  pressure that is not real. This is older than this release.
- `DROP INDEX` does not remove the constraint a `CREATE UNIQUE INDEX` installed, and `CREATE TABLE`
  is refused on a namespace that already carries a constraints-only schema.
- A cold point read costs about 0.5 ms in disk mode. The first scan after a restart still grows
  a little faster than linearly with the namespace size.
- Issue #43 stays open pending the nightly Linux soak (see above).
- `Coordinator.updateSubscriber` can still drop subscriber-state updates when its buffer is full,
  and closed in-memory stream clients are never removed from their hub (#120's follow-ups).
- A power loss that persists a later page of a write batch before an earlier one leaves intact
  frames after a hole. Neither commit was acknowledged, but #129's rule refuses it as damage —
  the safe direction — so such a namespace needs `repair-segments` rather than opening by itself.
