# v0.9.0

A feature release built around serving qtask's production workload (#304). Reads, counts and
expiry no longer read every document body, a crashed node reopens in seconds instead of
rebuilding its indexes, and queries are bounded by memory accounting instead of risking an OOM
kill. It also adds SQL for absent fields, revocable access tokens and an arm64 image, and fixes
unbounded memory growth on single-CPU deployments (#303).

**Two things to act on when upgrading** (details in [Upgrading](#upgrading)):
- `@kdb/client` must move to 0.9.x together with the server. Before 1.0 a client only accepts a
  server of the same minor version.
- Without `--rbac`, `kdb-service` now refuses to serve `--control-addr` on a non-loopback address
  unless you pass `--control-open`.

## Performance

Measured with the new `go/cmd/kdb-qtask-sim`, which replays qtask's dataset shape and SQL over
the wire. The dataset had 20,000 tasks and 116,400 documents, run with `--durability sync
--expire-field _expireAt`. v0.8.2 and v0.9.0 opened copies of the same data directory, written by
v0.8.2. The machine was a shared macOS laptop, so treat the ratios as the result, not the
absolute times.

| statement (heaviest user: 2,278 tasks) | v0.8.2 | v0.9.0 |
| --- | ---: | ---: |
| `COUNT(*)` of tasks under `--expire-field` | 3 m 39 s | 1.5 ms |
| `COUNT(*)` of the namespace | 16 s | 0.2 ms |
| exact indexed count (unread notifications) | 25 s | 0.7–4 ms |
| keyed read of 200 tasks | 2.3 s | 28 ms |
| whole-document scan of one user's tasks | 35 s | 0.5 s |
| task list (2 lean reads + 200 keyed) | 50 s | 0.3 s |
| **mixed workload, 8 users** | **1.1 actions/s** | **121.6 actions/s** |
| restart after `kill -9`, until listening | 47–54 s | 2.1 s |

What changed:

- **Counts and expiry without reading bodies.**
  - With `--expire-field`, a system index on the expiry field picks out the expired documents.
    Only those bodies are read, to confirm them. The sweeper used to read the whole namespace
    every minute.
  - `COUNT(*)` with an AND of exact equalities and `IN` lists is answered from index id sets.
    Other counts stream instead of materialising rows.
- **Bulk-written documents read cheaply.** A commit that writes 64 KiB or more of bodies now
  stores each body by value in the blob store, instead of as a pointer into the commit's
  multi-megabyte frame. Before this, 98% of read CPU went to decompressing whole frames to reach
  one document. Data written by earlier versions is re-filed the first time such a frame is read.
  One-document commits are unchanged.
  - This stores bulk-written bodies twice (log and blob store). Set `KDB_LARGE_COMMIT_BODY_BYTES=-1`
    (`StorageEngineConfig.LargeCommitBodyBytes` when embedding) to turn it off.
- **Predicates and projections decode one field at a time.** They no longer decode a whole
  document, so an embedding never has to be decoded to filter on a short field.
- **Paged and sorted reads stop early.** `ORDER BY kdb_id` / `kdb_id > ?` pages stop at their
  `LIMIT`. Other `ORDER BY … LIMIT` queries keep only the best `LIMIT + OFFSET` rows while
  candidates stream. An oracle test checks this against a full sort.
- **`ORDER BY <col> LIMIT k` walks a BTREE on `<col>` (#305, Go).** When the WHERE has an index
  path and `<col>` has a single-field BTREE, the executor reads documents in key order and stops
  once the page is settled. A 200-row page of a user with 8,000 tasks, `ORDER BY dueDate LIMIT
  200`, reads 210 documents instead of 8,000. Results are unchanged: a randomized oracle runs
  7,560 queries against the full sort. Only ascending order on a top-level column is served
  this way; DESC and other shapes use the bounded top-k above.
- **Fast reopen after a crash.** After an unclean stop, indexes catch up from their snapshots by
  diffing document trees, instead of being rebuilt from every document. Missing indexes are built
  in one scan, and all indexes share one parse per document, on the commit path too.
- **Queue claims scale with workers.** Measured at 29, 182 and 164 claims/s with 1, 8 and 64
  workers. Group commit already covered transactions; the collapse qtask saw came from the
  claim's lean read, which the body changes above fixed.

### OR in a WHERE clause is served from indexes

This shipped in v0.8.2 (#298), but v0.8.2's notes wrongly said its server code was identical to
v0.8.1, so it is described here.

**An OR in a WHERE clause is served from indexes instead of a full scan** (Go and Kotlin
servers). Index selection used to consider only top-level AND conjuncts, and an OR was never one
an index could serve, so a filter like

```sql
SELECT kdb_id, _doc FROM docs WHERE _c = ? AND (userId = ? OR collaborators.userId = ?)
```

read every document in the namespace even with an index on each field. That is the shape of a
typical "owner or collaborator" access-control filter. Now, when every disjunct of an OR can be
served (by `=`, a range, `BETWEEN`, `IN`, a `kdb_id` key, an AND with at least one servable
conjunct, or a nested OR that is itself servable), the OR is served by the union of those
lookups. The whole WHERE is still re-checked on every candidate, so results are unchanged. An OR
with any disjunct that has no index still scans, as before.

- The Go plan label is `index:or(...)` with one entry per disjunct, e.g.
  `index:or(eq(userId)|eq(collaborators.userId))`. Kotlin's EXPLAIN access path is
  `UnionScan(...)`.
- Go costs an OR as the sum of its disjuncts' estimated sizes, so a cheaper single conjunct (such
  as `taskId = ?`) is still preferred, and a small OR is preferred over a large conjunct such as a
  shared collection tag. `IN` lists are now costed too (the sum of their values' counts).
- The union is deduplicated and in document id order. Paged SELECTs (including keyset pages),
  `COUNT(*)`, `UPDATE` and `DELETE` with such a WHERE use it too.
- Measured in `TestOrUnionAvoidsTheScanAtScale` (in-memory storage, 20,000 documents):
  `_c = 'tasks' AND (userId = ? OR collaborators.userId = ?)` went from 26.6 ms (20,000 rows
  examined) to 4.5 ms (1,928 examined). The 3-way form with `OR projectId IN (?, ?)` went from
  29.0 ms to 12.5 ms (5,213 examined).
- Kotlin chooses the first servable conjunct rather than the cheapest, since it has no costs. So
  an indexed AND conjunct ahead of the OR is still used there instead of the union. Kotlin also
  only plans indexes on fields its schema declares indexed.

## Fixes

**Memory growth on single-CPU deployments (#303).** With one CPU (`GOMAXPROCS=1`: a single-core
VM or a container limited to one CPU), a namespace under sustained updates did not reuse the
memory of dropped document-tree versions fast enough, and the live tree's memory grew without
bound. In a benchmark it reached 4–7× the tree's size and was still growing. It now settles at
the same size as on multi-core machines, about 1.5× the tree. Updates on one CPU cost about 5%
more: that is the garbage-collection work that had been skipped. Multi-core deployments are
unaffected.

**Queries fail with `RESOURCE_EXHAUSTED` instead of OOM-killing the node.** Admission now sizes a
query from its plan (index candidates, page size, `LIMIT`; nothing for `COUNT(*)`), and caps a
grant at half the node's capacity instead of refusing it. What a query actually holds is charged
as it runs (`QueryContext.RetainedLimit`). Past that, the query fails with `RESOURCE_EXHAUSTED`.

**Backups carry their namespace's definitions.** Control-plane namespace backups now include the
schema, unique constraints and indexes. `kdb-inspect restore` and the control-plane restore keep
them, and `kdb-service` adopts them at its first open.

## New

**SQL** (Go and Kotlin servers; Kotlin since #307):
- `IS MISSING` / `IS NOT MISSING` and `EXISTS(path)` tell an absent field from a stored null.
- `ALL_VALUES(path)` returns every value a path through an array reaches. A bare column still
  projects the first value, per spec §3.5.
- A projected JSON boolean is typed `BOOL`. Its wire text is still `1`/`0`.

**Typed, paged reads:** `QueryValuesPages` (Go) and `queryValuesPages` (TS).

**Revocable access tokens** (with `--rbac`). Issue a client a `kdbt_…` token that carries a user's
roles and can expire, with `kdb-service token create|revoke|list`. The registry stores only each
token's SHA-256. The Kotlin server reads and verifies the same token records and can create and
revoke them (#307). Tokens are accepted as the bearer token or as the password.

**Kotlin servers** also gained the bounded top-k for `ORDER BY … LIMIT` (#307). They used to load
and sort every candidate.

**`--expire-namespaces`** applies the `--expire-field` policy to namespaces opened on demand, by
name or pattern (e.g. `qtask/*`). Default empty: expiry applies to `--namespace` alone, since it
deletes data.

**`kdb-qtask-sim`** (`go/cmd/kdb-qtask-sim`) loads, probes and benchmarks a qtask-shaped workload
over the wire.

**The container image is published for linux/arm64** as well as linux/amd64.

## Upgrading

**Clients.** `@kdb/client` 0.8.x refuses a 0.9.0 server, and 0.9.x refuses a 0.8.x server: before
1.0 a client only accepts a server of the same minor version. Upgrade servers and clients
together. From-source (`0.0.0-dev`) servers are accepted by any client.

**Control plane.** Without `--rbac`, the control plane cannot tell one caller from another. So
`kdb-service` now refuses to start when `--control-addr` is not a loopback address, unless you
pass `--control-open` to accept that. Either turn on `--rbac` (and issue access tokens), bind
the control plane to loopback, or add `--control-open`. Loopback and empty addresses are
unaffected.

**Disk use.** Bulk-written bodies are stored twice (see Performance). Existing data grows as its
large frames are first read and re-filed. Set `KDB_LARGE_COMMIT_BODY_BYTES=-1` to keep v0.8.x's
layout.

**Servers.** Replace the binary and restart, node by node.

**Rolling back to v0.8.2 is safe for data.** v0.9.0 keeps the on-disk format: v0.8.2 opens a
data directory written by v0.9.0, after a clean stop or a `kill -9`, and reads the same documents
and index results. Bodies filed by value, the expiry index and the RBAC registry all carry over.
Rolling forward to v0.9.0 again sees everything v0.8.2 wrote. Before rolling back:
- Remove `--expire-namespaces` and `--control-open`. v0.8.2 refuses to start with flags it does
  not know.
- Namespaces covered only by `--expire-namespaces` stop expiring under v0.8.2. Documents there
  that expired but were not yet swept become readable again until v0.9.0 is back.
- Move clients from access tokens back to passwords. v0.8.2 rejects tokens; they work again
  after rolling forward.
- Expect a slower open after an unclean stop. v0.8.2 does not catch indexes up from snapshots
  (35 s vs 7 s on a 15,000-document test).
- Move `@kdb/client` back to 0.8.x as well (see Clients).

## Known issues

- Kotlin servers do not walk a BTREE for `ORDER BY … LIMIT` (#305 is Go only); they use the
  bounded top-k.
- A node does not yet accept connections while it is opening. After a crash, opening now takes
  about 2 s at qtask's scale.
- `@kdb/client` is not published to npm (no `NPM_TOKEN`). The package tarball is attached to the
  GitHub release.
