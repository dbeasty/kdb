# v0.8.1

A patch release for one **v0.8.0 memory regression**. It affects any deployment with many small
namespaces, such as one namespace per match, session or tenant. Upgrade if you run v0.8.0 that
way. There are no format, protocol or default changes, and v0.8.0 and v0.8.1 nodes mix freely in
a cluster.

## Fixes

**Every namespace held a 1 MiB commit-graph chunk from its first commit (#295).** v0.8.0 moved
the commit graph off the Go heap into fixed-size chunks. A namespace's first commit allocated a
full chunk (4,096 records, 1 MiB) however small the namespace stayed, so thousands of small
namespaces held about 1 MiB each, gigabytes of mostly empty graph. The first chunk now starts
small (16 records) and doubles up to the full size; later chunks are full size as before. A
namespace with a handful of commits now holds a few kilobytes of graph. Measured on `kdb-service`
with 2,000 namespaces of 3 commits each: Go heap in use **2,300 MiB on v0.8.0, 366 MiB on v0.8.1**.
Resident memory was similar on macOS, where the untouched chunk pages were never backed, but Go's
heap accounting, which drives garbage-collection pacing and `GOMEMLIMIT`, counted all of it.

**A corrupt SSTable footer can no longer size a huge allocation (#295).** A table whose trailer
declares an index longer than the file itself now fails at once with `ErrCorruptTable`, naming
the table, instead of the reader sizing an allocation or read from that length. A damaged table
was seen whose trailer decoded to about 456 million. This makes such damage fail fast; it does
not change how a healthy table is read.

**`kdb-service --help` no longer says RBAC users cannot be created (#296).** They can, with
`kdb-service user create --data-dir … --user … --password … --roles …` (and `user role` for
roles) before the service starts; the developer guide now documents it.

## New

**`graph.chunkBytes` / `KDB_GRAPH_CHUNK_BYTES`** sets the full size of a commit-graph chunk
(default 1 MiB, minimum 4 KiB). The default suits most deployments; a node with very many
namespaces that each grow large can lower it to trade a little more allocation for less unused
space. A namespace's genesis commit, stored before settings apply, is repacked to honour it.

## Upgrading

Replace the binary and restart, node by node, in any order. v0.8.1 reads and writes exactly
what v0.8.0 does, and rolling back to v0.8.0 is equally safe. Clients need no change.

## Known issues

v0.8.0's known issues still apply (`docs/releases/v0.8.0.md`). The per-namespace document hash
shard (`docHashShard`) already started small in v0.8.0; its heap in many-namespace deployments
has not been re-profiled since this fix.
