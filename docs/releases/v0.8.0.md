# v0.8.0

**There was no v0.7.2 release.** A small v0.7.2 was prepared on 2026-10-12 (index snapshots off
the write path, multikey unique constraints, indexes that follow the stored document), but it was
never tagged. Its changes ship here, with everything else since v0.7.1.

This release is about **data larger than memory**. A Go node now opens, reads, scans, writes,
checkpoints and bootstraps a peer at 10 million documents with every phase's peak heap within a
quarter of the data's size on disk: the worst phase, an empty node installing a 10M-document
snapshot, peaks at 501 MB against an 854 MB budget, where it took 15.7 GB and 34 minutes before
(now 2 m 58 s). The commit graph, the live document tree, live document bodies, the cold-read
indexes and SSTable indexes all moved off the Go heap into mapped files or bounded caches, and
the new layout is on by default.

It also adds **attachments** (named binary files per record, with Merkle content hashes, ranged
verified reads, deltas and peer transfer), a **client-side replica** for TypeScript and Kotlin,
**squash catch-up** for far-behind nodes, **binary wire frames** between clients and servers, and
much faster node sync: a 200,000-commit backlog joins in about 10 seconds instead of over a
quarter of an hour.

It is **0.8, not v0.7.2**, because of the format, default and protocol changes below.

## Behaviour changes — read before upgrading

**Upgrade clients together with servers.** `@kdb/client` accepts a server from its own release
line only (same minor version while the major is 0), so a 0.7.x client refuses a 0.8.0 server
unless it sets `skipVersionCheck`. All new wire features are negotiated per connection, so an
old client that skips the check still works over JSON, as an old server does with a new client.

**Attachments are one-way.** Once a namespace stores its first attachment, builds before v0.8.0
refuse its log. Their error suggests `repair-segments`: **do not run it on such a log**. In a
cluster, every node must run v0.8.0 before the first attachment is written; an older peer is
refused attachment commits with `UNSUPPORTED` and the mesh converges once all are upgraded.

**Storage defaults changed for `kdb-service` and the CLI.** The commit graph file (`graph.file`),
the paged live tree (`tree.file`) and bounded live bodies are on by default. The first open of an
existing namespace is slower once, while it writes the tree segment from the checkpoint. Opt out
with `KDB_GRAPH_FILE=off`, `KDB_TREE_FILE=off`, `KDB_BOUNDED_LIVE_BODIES=off`. Library embedders
who build `StorageOptions{}` themselves keep the old in-heap behaviour until they opt in. On
Windows, which cannot map files, the tree and graph stay in the heap.

**New on-disk layout.** Checkpoints are now v6 (the live tree and commits in a streamed, mapped,
CRC'd section) for namespaces past 20,000 entries or with graph segments, and v2 below that.
v3–v5 checkpoints are still read and migrate at the next checkpoint. New per-namespace
directories hold rebuildable caches and attachments: `graph/`, `tree/`, `deltaidx/`, `sstidx/`,
`sstable-partial/`, `attachment/`. SSTable names carry a per-namespace sequence, and merges write
runs of capped, size-tiered tables. Close no longer merges a store over 64 MiB; a background
merge starts at the next writable open instead.

**Downgrading to v0.7.1 works for a namespace without attachments, and costs one full log
replay.** Tested on 100k- and 200k-document namespaces built with v0.8.0's defaults (600k writes,
v6 checkpoint, tree segments, the new SSTable names): v0.7.1 opened them at the same head, served
the same values and took writes, and v0.8.0 then opened them again. v0.7.1 cannot read a v6
checkpoint, so its first open replays the whole log (24 s at 600k writes). It is **not** safe
for a namespace whose state is only in its checkpoint (one that joined by snapshot or squash
catch-up, or a `history=none` namespace whose log was truncated): v0.7.1 would replay a log that
does not hold it. **Never roll a namespace with attachments back to v0.6.x**: v0.6.2 reads the
first attachment commit as the end of the log and silently serves the state before it, dropping
every later commit (v0.7.1 refuses such a log with an error instead).

**Memory accounting.** The hot-tier budget's shares were re-cut to sum to 1.0 (they summed to
1.75): the document cache drops from 0.50 to 0.30 of the budget, the memtable from 0.25 to 0.20,
so memtables flush about 1.25× as often. Under a cgroup the memory guard no longer counts
reclaimable page cache; off a cgroup it no longer charges read-only mapped pages.

**Limits.** Peer-sync listeners cap connections at 64 by default (was unlimited; negative means
unlimited). A graft push is capped at 256 MiB (was 1 GiB). An unpaged SQL result over 15 MiB
encoded now fails with `RESOURCE_EXHAUSTED`, where the reply used to vanish and the client time
out. A stream catch-up over about 4 MiB arrives in several parts.

**SQL and clients.** An eligible paged `SELECT` (no `ORDER BY`, `DISTINCT`, `GROUP BY` or
`OFFSET`) now pages by key and returns rows in document-id order; tokens from older builds still
continue by offset. JDBC `getObject` returns typed values (Long, Double, null) instead of strings.

**Unique constraints over arrays are multikey, as in MongoDB** (from the unreleased v0.7.2). Each
array element is a claim of its own; `CREATE UNIQUE INDEX` over existing overlapping arrays is
refused. Go and Kotlin agree.

**Merges re-apply the branch's field changes**, not its whole documents, so a concurrent edit to
another field on the primary survives and a removed key is not revived (Go and Kotlin).

**Writers to a namespace being bootstrapped from a peer snapshot are refused at once** with
`BUSY` (retry after 1 s), instead of waiting out the install and timing out.

## New

**Attachments.** Named binary attachments per record (record id + unique name), content-hashed as
a Merkle tree over 1 MiB SHA-256 chunks, with an attachment table whose root each commit carries;
conflicts resolve per attachment. SQL: `INSERT … WITH ATTACHMENT`, `UPDATE … SET ATTACHMENT`,
`DROP`/`RENAME ATTACHMENT`, `_attachments`, `ATTACHMENT()`, `ATTACHMENT_COUNT/SIZE/MIME()` (Go
server). Resumable uploads; verified ranged reads in Go, TypeScript, Kotlin and JDBC (`Blob`);
damaged stored bytes surface as a typed `INTEGRITY` error. Versions are delta-encoded at any size
in budgeted, resumable jobs (`--attachment-deltas=false` keeps every version whole). Backups,
peer transfer (Go↔Go, Go↔Kotlin), `kdb file ls|put|get|rm|migrate`, and memory that stays flat
at 100k blobs.

**Client replica.** `@kdb/replica` (TypeScript, Node and browsers with IndexedDB) and
`kdb-replica` (Kotlin/JVM) keep namespaces locally and sync with a node over peer sync v2:
snapshot bootstrap, replay or squash catch-up, push-first sync, filtered namespaces with a
durable write-back outbox, live updates (`REFS_WATCH`), attachments with a bounded byte cache.
Kotlin full-mode namespaces persist on disk in Go's checkpoint format.

**Squash catch-up.** A node far behind a peer can jump to its head (`catchup=squash|auto` per
peer, `catchup-ns` per namespace) instead of replaying every commit: a 1M-commit backlog over
1,000 documents in 0.73 s against 49 s. The skipped history can be deepened later. The default
stays `replay`; a namespace can refuse squashing (`PUT /v1/ns/{ns}/catchup`).

**Binary wire frames.** Clients and servers negotiate binary (and zstd) frames per connection in
Go, TypeScript and Kotlin/JDBC, with typed SQL cells: `SELECT *` over 200 rows 811 → 188 µs.

**Kotlin and Go share checkpoints.** Kotlin opens a namespace from Go's checkpoint (v2, v4–v6)
instead of replaying the whole log, writes Go-format checkpoints byte for byte, and bootstraps
from a snapshot in both directions. Kotlin peer sync v2 transfers attachment blobs.

## Performance

**Against v0.7.1, v0.8.0 is faster in every row measured, with its new defaults on** (graph file,
tree file and bounded live bodies, which keep memory flat at scale). Workload matrix, each version
with its own harness and defaults, 4 interleaved rounds under one lock; reads time-based,
memory-only writes at a fixed 50,000 operations so both see the same store size; Apple M3 Max,
macOS, load 4–7 (every round agreed on the direction):

| Row (ops/s, median) | v0.7.1 | v0.8.0 | Change |
| --- | ---: | ---: | ---: |
| memory-only insert, single-user | 49,316 | 54,254 | +10.0% |
| memory-only insert, heavy multi-user | 39,187 | 41,373 | +5.6% |
| memory-only update, single-user | 55,456 | 62,809 | +13.3% |
| memory-only update, heavy multi-user | 41,091 | 45,034 | +9.6% |
| reads, single-user, overlapping | 4,351,928 | 4,783,136 | +9.9% |
| reads, heavy multi-user, overlapping | 21,590,841 | 26,796,050 | +24.1% |
| reads, single-user, non-overlapping | 5,443,447 | 5,470,685 | +0.5% |
| reads, heavy multi-user, non-overlapping | 6,044,566 | 6,143,210 | +1.6% |

The fsync-bound write rows are left out: on macOS they are bimodal from disk contention and do not
compare across runs.

- **Memory at scale** (10M documents, 3.4 GB on disk): peak heap at open 1,456 → 11 MB, close
  2,077 → 43 MB, point reads 270 MB, a full scan 58 MB, a peer bootstrap 15.7 GB → 501 MB. At 1M
  documents, open takes 0.39 s instead of 19.6 s, with 201 MB of heap instead of 1,518 MB.
- **Node sync:** a 200,000-commit join takes about 10–13 s instead of over 14 minutes; pack pages
  are zstd-compressed between nodes that both support it (3.6× fewer bytes); a 10k catch-up
  allocates 246 MiB instead of 18.8 GiB.
- **Writes:** with 27 indexes, `CREATE INDEX` ×27 takes 0.3 s instead of 15–21 s and the
  per-commit p99 is 16–18 ms instead of 584–662 ms. Tree hashing resumes from a precomputed
  midstate: memory-only writes are 11–18% faster than before that change. Kotlin hashes on the
  JDK's SHA-256 (13.6× a tree fold on the JVM) and no longer copies the whole document map per
  write (1M documents: 69 ms → 97 µs per insert; `DocumentTree.build` 87 s → 0.8 s).
- **Close and merges:** close at 3M documents 11.0 → 0.57 s; SSTable merges stream (10M merge
  peak heap 1,523 → 261 MB) and are size-tiered (3.7× instead of 33.7× of flushed bytes written).
- **Reads:** the SSTable block cache is actually used (hit 2,130 → 126 ns); keyset paging over
  20k documents with `WHERE` 969 → 79 ms; stream fan-out to 128 subscribers takes half the time.

## Fixes

- A partial write (merge patch) no longer drops a document from the index of a field it left
  out (Go). Indexes built while it was live are repaired by a rebuild.
- `CREATE INDEX` under concurrent writes could lose entries or keep stale ones.
- Location records were lost under fast async writers and never filed on replay, forcing a
  whole-log cold index.
- Oversized replies vanished (client timeout); a far-behind subscriber looped forever on a
  >16 MiB delta; there was no write deadline, so a stalled peer could hold a connection's send
  lock; a handler panic over TCP/WS crashed the process.
- A two-peer join sent history twice; a `bootstrap=snapshot` peer could be skipped and full
  history fetched instead; nodes could wedge for minutes in the virtual merge base holding the
  write gate.
- The cgroup page cache could push the memory guard into its critical zone.
- A vector index could panic on the commit path after a search; an as-of read after a rebuild
  answered empty; `kill -9` between an index snapshot and its manifest could restore the wrong
  index.
- Merges lost concurrent primary field edits and revived removed keys.
- Kotlin: JDBC autocommit DML never committed; served pre-squash values for a squashed Go
  namespace; TCP framing was quadratic (multi-MB frames never arrived); `kdb-service
  --peer-sync` could not start; a concurrent-push race (`missing parent tree`).

## Upgrading

1. **Upgrade every node of a cluster, and every `@kdb/client`, to 0.8.0 before writing the first
   attachment.** A 0.7.x client refuses a 0.8.0 server unless it sets `skipVersionCheck`.
2. A rolling upgrade works node by node under load: a mixed v0.7.1/v0.8.0 mesh syncs (wire features
   are negotiated) and converges once upgraded. Tested with clean stops and `kill -9`, and with a
   2-old/3-new mesh with kills, against v0.7.1 and v0.6.2.
3. The first open of each large namespace writes its tree segment and is slower once.
4. If you need to roll back, read **Downgrading** above first: v0.7.1 is fine for a namespace
   without attachments that has its own full log; nothing earlier than v0.7 is safe once a
   namespace has attachments.
5. To keep v0.7.1's in-heap behaviour for a while: `KDB_GRAPH_FILE=off KDB_TREE_FILE=off
   KDB_BOUNDED_LIVE_BODIES=off`.

## Build, tests and CI

PR checks are sharded and cached (each shard about a minute); the full suites run nightly. A new
10M-document memory acceptance script (`scripts/memory-acceptance.sh`, with `BOOTSTRAP=1` for the
peer bootstrap) and a multi-node attachments e2e suite with real media.

Release testing for this build (commit on `release/v0.8.0`):
- Go: gofmt, `go vet`, the full suite without `-short`, and `-race` over storage, embed, peersync,
  replication, server, document and dag on macOS; whole-tree `-race` on Linux (nightly). It found
  one data race, in test scaffolding around the sorted snapshot copy (#289, fixed).
- Kotlin: `./gradlew build` (JVM, JS browser and Node, macOS native).
- TypeScript: `@kdb/client`, `@kdb/replica` (including live interop with a Go host).
- e2e on macOS: the default suite (127 passed), `slow` + `destructive` (33 passed), and the upgrade
  suite against v0.7.1. On Linux (GitHub runners): `slow` + `destructive`, the upgrade suite
  against both v0.7.1 and v0.6.2, and the `kill -9` soak.
- Downgrade to v0.7.1 by hand on 100k- and 200k-document namespaces (see Downgrading).
- Artifacts: `make release-all`, `make bundle-verify` (the embeddable bundle builds, tests and
  cross-compiles from the zip alone), and `make release-verify` (two clean builds are
  byte-for-byte identical).
- The 10M-document memory acceptance (`BOOTSTRAP=1 scripts/memory-acceptance.sh`) on main.

## Known issues

- **Windows** cannot map files: the tree and commit graph stay in the heap and SSTable sidecars
  are not written, so the memory figures above do not apply there. Windows support remains
  preliminary.
- A namespace that joined by snapshot or squash catch-up cannot be rolled back to v0.7.1 (its
  state is only in a v6 checkpoint), and one with attachments cannot be rolled back at all.
- The Kotlin server has no attachment SQL (Go only), and Kotlin peer sync has no graft, boundary,
  squash, filter, projection or watch; a Kotlin host serves one namespace.
- `TestTreeFileCheckpointSegment` failed once under heavy parallel load during release testing
  and not in 480 stressed runs since; tracked as a rare test flake.
