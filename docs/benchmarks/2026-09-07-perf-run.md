### `kdb/storage/engine` — genuine deadlock (Finding 2) — FIXED

```
BenchmarkReadBlobConcurrent/parallel-256-16  fatal error: all goroutines are asleep - deadlock!
```

**Root cause: a lost-wakeup race in `GroupCommitter.runRounds`**
(`go/kdb/storage/wal/group_commit.go`). The loop released `g.mu` between snapshotting an
empty batch and clearing `inFlight`:

```go
g.mu.Lock()
batch := g.waiters
g.waiters = nil
g.mu.Unlock()          // <-- window opens here

if len(batch) == 0 {
    g.mu.Lock()
    g.inFlight = false // <-- ...and closes here
    g.mu.Unlock()
    return
}
```

A `SyncTo` caller landing in that window appends its waiter, sees `inFlight` still true so
declines to start a round of its own, and is then abandoned when `runRounds` returns —
blocking on its channel forever. Because the abandoned goroutine is the *only* one left
with work, Go's runtime reports a total deadlock. This also explains why the crash dump
contained no `runRounds` goroutine: it had already exited.

It does **not** need concurrent writers. A single sequential writer with a fast `doSync`
reproduces it, which is why the package's existing tests never caught it — all of them
keep several waiters queued behind a sleeping `doSync`, which keeps batches non-empty and
hides the window entirely.

**Fix:** clear `inFlight` under the same lock hold that found the batch empty. A caller
then either lands before the snapshot (its waiter is in the batch) or after `inFlight` is
cleared (it starts a fresh round) — never in between. Added
`TestGroupCommitter_SequentialWaiterIsNeverAbandoned`, which hangs deterministically
before the fix and passes after.

**Verified:** `kdb/storage/wal` passes under `-race`; `BenchmarkReadBlobConcurrent`
parallel-256 now completes (5,490,174 iters, 213.5 ns/op) where it previously crashed.

## Finding 1: heavy-multi-user writes now fail outright

Reproduced with the documented baseline recipe, run alone on an otherwise idle machine
(confirmed via `ps`/`top` — no other heavy job running):

```
cd go && go test ./kdb/server/ -run '^$' -bench BenchmarkWorkload -benchtime 2s -count=5 -benchmem
```

**Fails 100% of samples (5/5)** with `workload_matrix_bench_test.go:235: kdb server:
deadline exceeded: timed out waiting for an earlier write to finish`:

| Benchmark |
|---|
| WriteInsert / heavy-multi-user |
| Update / heavy-multi-user / overlapping |
| Update / heavy-multi-user / non-overlapping |
| Durability sync-full / insert / heavy-multi-user |
| Durability sync-full / update / heavy-multi-user |
| Durability memory-only / insert / heavy-multi-user |
| Durability memory-only / update / heavy-multi-user |
| Durability async-100ms / insert / heavy-multi-user |

**Fails some samples:**

| Benchmark | Pass / 5 |
|---|---:|
| Transaction / heavy-multi-user / overlapping | 4 |
| Transaction / heavy-multi-user / non-overlapping | 1 |
| Durability async-100ms / update / heavy-multi-user | 1 |

**Why this is a new bug, not the known Trap 2 drift:** the `6d2b4bb` baseline documented
memory-only durability rows as *immune* to drift, because they never touch the WAL
("memory-only being immune points at accumulated WAL/disk state, not thermal" —
`2026-09-06-suite-rerun.md`). On `96762be`, memory-only heavy-multi-user insert/update
now fail outright too. Losing that immunity means the failure is in code shared by every
durability mode — the commit path, write ordering, or memtable/commit-DAG — not
WAL-specific accumulation. It also isn't resource contention: this exact result
reproduced twice, once contaminated by concurrent jobs and once alone on an idle machine.

**Unaffected:** all Read rows (see next section), all single-user rows, and — notably —
`BenchmarkWorkloadMixedReadWrite` (both variants) pass every sample, though with severe
drift (heavy-multi/overlapping ranged 24,475 → 17.62 ops/sec across 5 samples, with a
41MB/op allocation blowup on the last sample — concerning on its own, but not a hard
failure).

### Bisected: first bad commit is `63a53b0`

`git bisect` between `good=6d2b4bb` and `bad=96762be`, using

**`63a53b0` — "Bound the memory historical document trees hold"**

Endpoints are clean and directly verified: `6d2b4bb` passes at **30,461 ops/sec**
(matching the documented 30,051 baseline); `96762be` fails.

### Root cause: the commit path fell onto the tree-object rebuild

CPU profiles of `BenchmarkWorkloadWriteInsert/heavy-multi-user`, last-good (`63888f8`)
versus bad (`96762be`):

| Path | `63888f8` (good) | `96762be` (bad) |
|---|---:|---:|
| `runSchemaPhase` → `GetDocument` → `treeAt` | absent from top-200 | **45.15%** (8.19s) |
| ↳ of which `treeFromObjects` | — | **99.88%** of that |
| total CPU samples for the same 1s benchtime | 3.57s | 18.14s |

On every commit, `transaction.runSchemaPhase` resolves the transaction's base-version tree
via `store.GetDocument(ns, docID, base.DocumentTreeHash)`
(`go/kdb/transaction/default_engine.go:473`). Before `63a53b0`, `ServerEngine.treesByHash`
was an unbounded map that answered this with an O(1) hit. After, that lookup misses and
falls through to `treeFromObjects`, which reconstructs the tree by walking its diff-object
chain back to the nearest full object and applying forward — turning a map read into a
chain walk on the hot commit path.

Because the write gate admits one commit at a time (`writeGate.running` is a capacity-1
channel), inflating per-commit latency backs the queue up until waiters exceed
`DefaultWriteTimeout` and return `DeadlineExceededError`. That is the observed
`timed out waiting for an earlier write to finish`. It is independent of durability mode,
which is why memory-only fails too.

**Three plausible fixes were tested and disproven** — recorded so nobody repeats them:

1. *Eviction pressure — the budget is too small.* Forcing
   `ResolvedHistoryTreeBytes` to return `1<<40` (effectively unbounded) **did not help**:
   `treeFromObjects` still cost 47.95%. The miss is not eviction.
2. *The empty tree is no longer seeded.* `63a53b0` replaced
   `map[...]{emptyTree.TreeHash: emptyTree}` with a `newBoundedTreeStore` that starts
   empty. Re-seeding it via `e.treesByHash.Put(emptyTree)` **did not help**.
3. *`treeSizeBytes` walks the tree on every `Put`.* `DocumentTree.Size()` is O(1)
   (incrementally tracked), so `Put` is cheap. Not a factor.

So the trees the commit path asks for are genuinely never in the store it reads, and that
is true regardless of budget. The leading untested hypothesis is that the DAG's own tree
map — removed by this commit in favour of "the engine is the single owner and the DAG
reads through it" — was what previously answered these lookups, and that the engine's
store is populated from `e.tree` at publish time under a key that does not line up with
the `commit.DocumentTreeHash` the schema phase asks for. Confirming that, and deciding
whether the fix is to register each commit's tree under its own `DocumentTreeHash` or to
keep base-version trees resident (they are already `dag.Pin`-ned for exactly this
lifetime, see `server_runtime.go:602`), needs the judgement of whoever designed the
bounding — picking wrong risks reintroducing the unbounded 114MB growth that `63a53b0`
was written to fix.

## Methodology notes for next time

- **Never run this project's Go benchmarks concurrently with another heavy job** (another
  benchmark suite, a JMH run, a build) on the same machine. Contention alone produced a
  fake ~75% "regression" on a row documented as stable. Run one thing at a time, or at
  minimum rerun the Go workload benchmark alone before citing its numbers.
- The documented recipe (`-benchtime 2s -count=5`, `BenchmarkWorkload` filter) remains
  the right way to reproduce the workload family; `make bench`'s full-suite default
  timing intermixes many packages and is not directly comparable to the isolated
  baseline for this specific family.
- Compare Update/Mixed/Transaction heavy-multi-user rows **first-sample to first-sample**
  (they drift within a process); reads and single-user rows compare fine as medians.
