## Root cause, corrected: it is the objects history strategy, not `63a53b0`

Profiling the narrow reproducer (`memory-only/insert/single-user`) contradicts the
`2026-09-07-perf-run.md` diagnosis for this row. `treeFromObjects` does not appear in the
profile at all. 66.78% of commit CPU is `putTreeObject` → `DocumentTree.Walk` →
`trieWalkUntil`, with 1.88s of a 2.98s sample on one line - the full-tree walk at
`tree_objects.go:221`.

**The defect:** under the objects history strategy a *full* tree object is written every
32 commits to cap how long a historical read's chain gets. A full object is O(documents).
Dividing an O(n) cost by a fixed 32 commits means each commit carries n/32 - which grows
with the namespace forever, making total commit work quadratic in namespace size. The
comment claiming it "amortizes the full object across 32 commits" holds only if the tree
never grows.

**Provenance:** the objects strategy did not exist at the `6d2b4bb` baseline. It landed at
`407f05e` / `a6909bc`, *before* the `63a53b0` the earlier bisect fingered. `63a53b0` is
where per-commit latency crossed `DefaultWriteTimeout` - a threshold on top of an
already-growing cost, not the cause of it. That is why bisecting on a pass/fail predicate
pointed at the wrong commit.

**Measured**, single-user inserts as the namespace grows (memory-only, one writer):

| documents | objects (before) | objects (after fix) | replay (control) |
|---:|---:|---:|---:|
| 1,000 | 43.8 µs | 25.3 µs | 18.8 µs |
| 4,000 | 168.9 µs | 20.8 µs | 20.5 µs |
| 8,000 | 372.8 µs | 20.0 µs | 22.4 µs |

Replay is flat because it never had the cost; objects climbed linearly per insert, which
is the quadratic total.

## The fix

`treeChainFullAt` (`go/kdb/storage/engine/tree_objects.go`) decides when to write a full
object by **accumulated entries rather than object count**: a full object is written once
the chain behind it has cost as much as the full object would - rewrite when the delta
exceeds the base.

- **Writes** carry about one entry's worth of full-object cost per commit, whatever the
  namespace has grown to. Constant, not growing.
- **Reads** still cost at most twice their own floor: a resolution applies the full
  object's `size` entries plus a chain held to `size` of them, and rebuilding that tree
  costs that many entries either way.
- What it spends is *fetches*, not work - a chain may be up to `size` objects where it was
  32, each one memtable lookup paired with an entry the read had to apply regardless.

`treeFromObjects` takes its walk bound from the chain's own recorded length instead of a
fixed constant, with the configured `TreeChainLimit` as a floor so existing stores, and
chains whose in-memory counter a restart reset, resolve exactly as before. The on-disk
object format is unchanged.

Measured cost of the trade: a historical read at commit 2,000 of 4,000 went 20.3ms →
21.5ms, about 6%.

`TestTreeObjectWritesStayLinearInCommitCount` guards it by asserting that doubling the
commits roughly doubles the bytes tree objects write - 3.65x on the old code, 1.98x on the
new. It measures bytes rather than time so it fails on the defect, not on a slow machine.

## Finding 1 is two defects, and only one is fixed

Profiling `BenchmarkWorkloadWriteInsert/heavy-multi-user` after the fix shows a different
shape from the single-user row: 40.14% in `runSchemaPhase` → `GetDocument` → `treeAt` →
`treeFromObjects`, rebuilding trees through `DocumentTree.With` → `trieInsert` →
`internalHash` (sha256). That *is* the `2026-09-07-perf-run.md` diagnosis - it was right
about this row and wrong about the single-user one.

The open question that write-up left ("why does `treeAt` miss for a hash
`publishTreeLocked` should have stored?") has a straightforward answer, and it is not a
publishing bug: **concurrent writers legitimately ask for historical trees.** Each of the
1024 workers holds its own `tx.BaseVersion`, and the capacity-1 write gate means head has
advanced many commits by the time a transaction commits. So `base.DocumentTreeHash` names
an old tree, which misses `latestTree`, misses the bounded `treesByHash`, and gets rebuilt.
At `6d2b4bb` `treesByHash` was unbounded and answered every one of those lookups - which is
exactly why bounding it in `63a53b0` shows up here.

Note also that this fix makes each such rebuild apply more entries, since chains are
longer. Measured on this row it did not make things worse (it fails 3/5 where it used to
fail 5/5, and the surviving samples changed little), but it is a real interaction to keep
in mind when fixing the second defect.

**Next: keep base-version trees resident for their transaction's lifetime.** They are
already `dag.Pin`-ned for exactly that window (`go/kdb/server/server_runtime.go:602`), so
the pin is the natural place to hang residency off.

> **Superseded — and this specific suggestion is wrong.** Pinning at the `dag.Pin` site does
> not work: `Upsert` resolves head and *then* queues, and the tree is evicted before
> `runTransaction` is entered, leaving `treeFromObjects` at 45% of CPU. The pin has to be
> taken where the base is resolved. See
> [`2026-09-08-base-tree-pinning.md`](2026-09-08-base-tree-pinning.md) before acting on the
> paragraph above. The constraint from
`2026-09-07-perf-run.md` still stands: do not fix it by making the tree store unbounded
again - `63a53b0` exists because one historical read on a 16,000-commit namespace took a
process from 17.41MB to 114.74MB permanently.
