# Wire path: bounded replies, fewer copies (2026-10-13)

A/B for PR #170 (wire path: bounded replies, fewer copies) and its follow-up, which skips the byte scan when a reply's worst-case size already fits. Base is `origin/main` at 529408e. New is `perf/wire-path` including the follow-up commit.

## Method

- **Machine:** Apple M3 Max, darwin/arm64, Go 1.26.3.
- **Isolation:** every run went through the shared `bench-lock.sh`, which waits for the lock and for a 1-minute load average below 6. Base and new were run inside one locked invocation.
- **Interleaving:** base and new alternated in 8 rounds of `-count=1 -benchmem`, from pre-built test binaries. benchstat ran over the 8 samples per side.
- **Codec micro-benchmarks:** they are new in this PR. The base side used a copy that compiles against main, with the same names and the same messages.
- **Noise:** allocations do not depend on load; ns/op does. The load average is reported for each table.

The first run, before the follow-up commit, showed `star-200` at **+16.9%** sec/op, even though it used 64% fewer bytes. Measuring every cell's escaped length for the byte cap cost about 140 µs on a 200-row result. The follow-up accepts any result whose raw size times six (the worst-case escape) fits the cap after one pass over the cell lengths. With that change, `star-200` is **-7.9%**. `count-1000` is +1.3%, about 0.6 µs. The likely cause is the per-frame reply-budget reservation (two mutex round trips), which is within what we accept for a 0-row reply.
