# v0.7.1 release benchmarks: v0.6.2 vs v0.7.1

Date: 2026-10-12. v0.7.1 = `9055017` plus the release commits (no engine change in them);
v0.6.2 = `afa9351`. Machine: Apple M3 Max (16 cores), 48 GiB, macOS 26.5.2, Go 1.26.3. This
machine is shared with other sessions, so load and disk I/O were checked before every run.

**Verdict: no regression.** Reads got faster, writes and durability modes are unchanged
(within ±4%), and at 1M documents disk mode is usable where v0.6.2 is not. Past 10,000 documents
v0.6.2 returns wrong scan results (#115), so v0.6.2 has no valid scan timings to compare against.

## Workload matrix

```
go test -c ./kdb/server/   # once per version, then from go/kdb/server:
./server.test -test.run '^$' -test.bench BenchmarkWorkload -test.benchtime 2s -test.count 5 -test.benchmem
```

`workload_matrix_bench_test.go` is byte-identical at both tags, so the harness is the same.

### Reads: one run per version, load 3-4, no other disk activity

| Row (ops/s, median of 5) | v0.6.2 | v0.7.1 | Δ |
|---|---:|---:|---:|
| single-user / overlapping | 3,924,642 | 4,897,723 | +24.8% |
| heavy-multi / overlapping | 14,445,816 | 22,549,648 | **+56.1%** |
| single-user / non-overlapping | 5,526,825 | 5,915,658 | +7.0% |
| heavy-multi / non-overlapping | 5,841,252 | 6,226,321 | +6.6% |

Allocations are unchanged at 176 B/op and 4 allocs/op. v0.6.2's heavy-multi/overlapping
matches the 2026-09-22 full run (14.97M), so that baseline holds.

### Writes and durability: re-run back to back, v0.6.2 08:14-08:37, v0.7.1 08:37-09:03

The first pass is discarded. During its v0.6.2 half, another session's 5-node e2e cluster
fsynced heavily (~4,000 disk tps). That cut v0.6.2's sync-full rows by 2-10x, which looked like
a +100-1000% gain for v0.7.1. On macOS, any other process doing heavy flushing slows every fsync on the device.

Heavy-multi Update, Mixed and Transaction rows drift within one process, so those rows compare
the first sample. Every other row compares the median of 5.

## Disk mode (`--durability sync`, sync-mode full)

`go/cmd/kdb-diskbench`, run as in [disk-mode.md](disk-mode.md), started at load 3.9 with disk
under 800 tps. To run it against v0.6.2, the same source was built without the `memtune` call;
v0.6.2 has no GC pacing.

| v0.7.1 | 10k | 100k | 1M |
|---|---:|---:|---:|
| Bulk write (1,000-doc commits) | 53,824 docs/s | 54,855 docs/s | 48,419 docs/s (20.7 s) |
| Single-doc commit p50 / p99 | 4.81 / 6.90 ms | 4.10 / 7.94 ms | 4.12 / 7.87 ms |
| Point read, hot p50 / p99 | 0.33 / 1.9 µs | 0.83 / 2.9 µs | 1.0 / 2.6 µs |
| Point read, after restart p50 / p99 | 507 / 913 µs | 532 / 875 µs | 527 / 1,553 µs |
| Restart (open) | 0.12 s | 1.0 s | 10.6 s |
| Filtered SELECT, hot p50 | 10.8 ms | 121 ms | 1,462 ms |
| Filtered SELECT, first run after restart | 35 ms | 668 ms | **24.6 s** |
| RSS after load / after restart + scans | 93 / 49 MB | 203 / 206 MB | 702 / 1,259 MB |

These match the post-fix figures in [disk-mode.md](disk-mode.md): a 1M load of 19.8 s, a first
post-restart scan of 21 s, and 1,289 MB after a restart and scan.

**v0.6.2.** At 10k documents its load phase matches v0.7.1:
- 52,286 docs/s bulk write.
- Commit p50 4.11 ms.
- Hot point read p50 0.54 µs and p99 7.4 µs (v0.7.1: 0.33 and 1.9 µs).
- A keyed `kdb_id = ?` SELECT takes 5.5 ms; v0.7.1 answers it by key in under 0.01 ms.

v0.6.2's reopen phase at 10k, and its 100k run, stop at the benchmark's correctness check:

```
select_scan_bucket: got 99 rows, want 100
select_scan_one_row: got 0 rows, want 1
```

That is the result truncation fixed in this release (#115). On the pre-fix tree, the 1M figures
in disk-mode.md were 955 s to load and 26.6 min for the first scan after a restart.
