# KDB — Finish-Up Plan: Missing Functionality, Bugs, Test Gaps, E2E, Deployment

## Context

KDB is a portable embedded database engine ("source control for structured documents") with two parallel implementations of one spec (`docs/kdb-spec.md` + ~60 layer/component spec files):

- **Kotlin Multiplatform** (~50 `kdb-*` Gradle modules): original implementation, targets JS/JVM/Native. Includes JDBC driver, SQL layer, storage engine (WAL/memtable/SSTable/compaction), indexes (hash/btree/fulltext/vector), peer-sync, transports, server/service, CLI, inspect tooling.
- **Go port** (`go/`): native server, CLI, `database/sql` driver, WASM, peer-sync. Current branch `go-peersync-service-frontdoor`; recent work is Go peer-sync (divergence resolution, write-back stream, stream coordinator listener, WS client Connect).

The user's goal: a handoff plan for a different model to (1) fix bugs, (2) fill missing functionality, (3) close test gaps including full e2e testing, and (4) get the project deployable.

**User decisions (fixed):** (1) The **Go server** is the production deployment target ("zero JVM processes", per layer-12 execution plan); Kotlin stays the reference/embedded implementation and must remain correct. (2) Scope is **everything in the specs**, phased: deployable core first, then full spec completion (Layers 13/14/15, stored procedures, indexes, GPU). (3) Full e2e testing required, extending the existing Python pytest harness.

The Findings sections below are the evidence base (all file:line references verified by exploration agents); the Plan section is the phased roadmap for the executing model.

## Findings

### A. Tests / CI / Deployment cross-cut (agent 3 — complete)

**Confirmed live bugs (spot-checked on HEAD):**
- SSTable block CRC never verified on read: `go/kdb/storage/sstable/codec.go:31` writes `CRC32All(body)` at offset 8 but `decodeBlock` (lines 36–44) never reads it; footer SHA-256 also never read back. Same bug in Kotlin `SsTableCodec.kt:24-29`.
- Go peer-sync front door is **unauthenticated**: `go/kdb/peersync/host.go` threads `auth.Engine` through `NewHost`/`NewConnectionHost`/`newFrameHandler` (lines 34, 43, 76, 102) and `go/kdb/server/peersync_listen.go:81` passes it in, but no `Authorize` call exists anywhere in the package. Kotlin's `PeerSyncFrameHandler.kt:45-69` does enforce `AuthAction.PeerSync`.
- CI Go version mismatch: `.github/workflows/ci.yml` pins go 1.24 but `go/go.mod` requires 1.26.0 → Go CI jobs fail today.
- Stale/orphaned modules: `kdb-integrity/` and `kdb-recovery/` exist in tree as `build/` output only; sources live on unmerged branch `recovery/kotlin-verify-repair-restore` (commit 51bd876, not an ancestor of HEAD); `settings.gradle.kts` does not include them.
- Session tokens stored as plaintext document fields (`kdb-auth/.../token/SessionIssuer.kt:51-61`).

**CI gaps (`.github/workflows/`):**
- `ci.yml` is `workflow_dispatch` only — push/PR triggers commented out ("re-enable when CI is stable again"). Nothing runs automatically.
- Full Kotlin suite (`./gradlew test`, 67 test classes) never runs in CI — only `:kdb-integration:test` + `e2ePython`.
- `go-interop` job runs without `-tags interop` and without `KDB_JVM_SQL_WS_URI` → both JVM-server interop tests silently skip; CI never starts a JVM server for the Go client.
- Golden fixtures (`go/testdata/golden/codec/`, only 3 files) generated by hand via `ExportGoldenTest.kt` — no freshness check.
- `s3integration` (LocalStack) tests never run in CI; docker behavior harnesses (`docs/benchmarks/lightsail-sim`, `resource-governance-sim`) are manual only.
- No lint gates (gofmt/go vet/staticcheck/ktlint), no caching, no matrix, no macOS runner despite macosArm64 target.
- No release pipeline: no tag trigger, no artifacts, no container images, no maven/npm publish, no version string anywhere (no `version=` in any build.gradle.kts, no Go version constant).
- `benchmark.yml` (untracked): weekly JMH run — fine, needs committing.

**Test infrastructure that exists:**
- Kotlin `kdb-integration`: 14 test classes / 2,373 lines — WS peer sync (incl. two-client, bidirectional concurrent disjoint-doc merge), stream mode + fallback, branch accept/reject, document locks (5 scenarios), SQL transactions/pipelining/multi-client, auth handshake + RBAC via SQL, Flyway via JDBC. All drive **in-process hosts / loopback**, not real listening sockets.
- Python e2e (`kdb-integration/e2e/`): only 6 test functions / 198 lines, CLI-only one-shot subprocess smoke tests (init/put/get/query/shell/errors). Runs JVM CLI by default; `KDB_CLI_BIN` can point at Go binary but CI never sets it. **No server is ever launched by the e2e harness.**
- Go: 72 `_test.go` files; interop golden codec tests (3 fixtures); env-gated JVM WS interop tests; `go/kdb/integration/smoke_test.go` incl. real cross-language on-disk test (`TestKotlinPutThenGoGet_InteropDelta`); raw-socket 8-way concurrent commit test (`wire_listen_test.go`).

**Uncovered test scenarios (concrete):**
- Multi-peer (3+) sync / transitive propagation — all tests are 1 host + ≤2 clients.
- Concurrent conflicting writes to the *same* document over peer sync (Component 39 conflict path has no integration test; the concurrent test only asserts disjoint-doc auto-merge).
- Crash recovery / kill -9 (layer-13 test plan `killDashNineAnyPoint` doesn't exist; only orderly-abort sim).
- Real concurrent socket clients against a Kotlin listening server (Kotlin tests are in-process `handleFrame`).
- Disconnect mid-transaction over a real socket.
- Large data / long-running / compaction-under-load / restart-with-large-history (replay-after-restart OOM is a *known* untested hazard per layer-13 README).
- Auth end-to-end over network; token/session expiry (no tokens exist); TLS (zero tests anywhere).
- Python e2e: no server lifecycle, multi-client, corruption/restore, kdb-inspect, or Go/Kotlin differential runs.
- None of layer-13's 11 named tests exist as automated tests.

**Deployment gaps:**
1. No product container image (only benchmark Dockerfile — good multi-stage/non-root starting point at `docs/benchmarks/lightsail-sim/Dockerfile`). No JVM service image.
2. **No Go TLS at all**: `go/kdb/transport/ws/transport.go:62` returns "wss:// not yet implemented"; `go/kdb/config/config.go` declares `TLSConfig` that nothing consumes. Kotlin has TLS (`ServiceTls.kt`, PKCS12, mTLS JVM-only).
3. No health/readiness endpoints in either implementation.
4. No metrics exposition (`go/kdb/metrics/stage.go` is internal only — no Prometheus/expvar/pprof HTTP surface).
5. No structured logging (single startup printf; no levels/JSON).
6. Go server ignores config files: `cmd/kdb-service/main.go` never calls `config.LoadProduct` — flags only, no env vars.
7. RBAC/auth registry is in-memory-DAG in both servers (doesn't survive restart); no CLI way to create a user on the Go server.
8. No backup tooling: Layer 15 Component 60 (backup manifest → object storage) unimplemented; S3 sink is a byte copier, not restorable backup. Component 62 (peer backfill) absent.
9. Restore/verify tooling Go-only (`go/cmd/kdb-inspect` has verify/repair-segments/restore; Kotlin inspect lacks them — sources on unmerged branch).
10. No systemd unit / compose file for the service despite `--abort-after` exit-75 design requiring a supervisor.
11. No graceful drain of in-flight requests on SIGTERM, no connection cap, no rate limiting.
12. Kotlin servers launchable only via Gradle (no application/distribution/shadow plugin; no `java -jar` path).

**Spec/planning-doc status (with spot-check results):**
- Layer 12 execution plan: components 38/39/40/41/44/45/46 claimed done — spot checks confirm 39, 44, 45, 46 landed. Still open: auth-registry durability (both servers), token hardening. One unchecked box: "zero JVM processes, load-tested" exit criteria.
- Layer 13 (resource governance, comps 47–52): 47 partial, 50 done (supervisor/exit 75), 51 partial (typed errors), 49 only the bounded-write-queue half (no CPU governance/CoDel/scan budgets/conn cap), **48 (memory admission/cost model) not implemented** (help text in `cmd/kdb-service/main.go:44` admits it), **52 (federated backpressure) not implemented**.
- Layer 14 (encryption at rest, comps 53–57, untracked spec): **zero implementation** (no kdb-crypto, no go/kdb/crypto, no cipher imports). Its §2 survey flags the plaintext leaks + the two confirmed bugs above.
- Layer 15 (integrity/backup/recovery, comps 58–62): 58/59/61 exist in Go; 60 + 62 absent; Kotlin port unmerged.
- User guide explicitly lists as not done: published artifacts, `jdbc:kdb://` network URLs (throws SQLFeatureNotSupportedException), full git-style CLI, stored-procedure wire frame/CLI.

### B. Go tree (agent 1 — complete)

## Plan — Phased Execution Roadmap

### Phase 0 — Unbreak CI (do in this exact order)

CI is currently `workflow_dispatch`-only and would fail if triggered. Fix failures FIRST, re-enable triggers LAST.

Test: existing `go/kdb/server/stream_listen_test.go:84` passes under `cd go && go test -race -count=50 ./kdb/server/ -run TestStream`.

1. **Go peer/stream `Namespaces` handshake field crashes the JVM server** — `go/kdb/wire/payload_mapper.go`: `HandshakePayload.Namespaces` marshaled as JSON `null` when left at its Go zero value (e.g. `client.Connect`, which legitimately has no single target namespace at handshake time); Kotlin's `HandshakeDto.namespaces` is non-nullable `List<String>`, so `kotlinx.serialization` throws and the whole connection is torn down. 2. **Every wire DTO `[]byte` field was cross-language-incompatible** — Go's `encoding/json` marshals `[]byte` as a base64 string by default; Kotlin's plain `ByteArray` fields (no custom serializer on any of them) expect a JSON array of numbers. Added `go/kdb/wire/payload_dto.go`'s `jsonByteArray` type (custom `MarshalJSON`/`UnmarshalJSON` matching Kotlin's array-of-ints shape) and switched all 7 affected DTO fields to it.
3. **`TestConcurrentCommitsRacingSameBaseVersion` was not a concurrency bug** — investigated at length (bisected against clean HEAD, instrumented `defaultEngine.Commit`/`CommitTree` with an in-flight counter and a causally-ordered trace) because it failed deterministically under `-race` yet showed zero concurrent entry into the commit path. Root cause: the test seeded the base document with `{"v":0}` and one of its 8 racers also writes `{"v":0}` — since KDB's conflict detection is content-addressed ("the document is always the truth"), a write that reproduces the exact current content is indistinguishable from a no-op and correctly slips through without a conflict, which then masks the next racer too. This is real KDB semantics, not a bug — fixed the test (`go/kdb/client/client_test.go`) to seed with a value no racer ever reproduces.
4. **Component 40's direct-document wire API (`DocumentGet`/`Upsert`) was never ported to Kotlin — not the wire messages, not the underlying runtime methods.** `kdb-wire`'s `WireMessageType` enum tops out at `SESSION_BEGIN_ACK(0x13)`; Go's `MsgDocumentGet`/`MsgDocumentGetResult`/`MsgUpsert`/`MsgUpsertResult` (0x14–0x17) have no Kotlin counterpart at all, and there's no `getDocument`/`upsert` on Kotlin's `KdbServerRuntime` either. - **1-K3 DONE (WAL record format + corruption handling + truncate; segment rotation/multi-segment reopen ordering deferred - see below).** `kdb-storage-wal`:
  1. **Timestamp never persisted**: `WalCodec.encodeRecord` never wrote `record.timestamp` at all; `decodeRecords` fabricated `KdbTimestamp.now()` for every replayed record (`WalRecord(seq, KdbTimestamp.now(), kind, payload)`), so anything downstream of WAL replay that cares when a write actually happened (e.g. LAST_WRITE-style ordering) silently got "now" instead. Fixed by adding an 8-byte `epochMicros` field to the record header (`KdbTimestamp.toEpochMicros()` / `.fromEpochMicros()` round-trip exactly, since `KdbTimestamp` is millis+microRemainder rather than a bare long). New layout: `magic(4) bodyLen(4) sequence(8) epochMicros(8) kind(1) payloadCrc(4) payload(N) headerCrc(4)`. **Bumped `WalCodec.MAGIC`** (`0x4B444257` -> `0x4B444358`) since this is a breaking on-disk format change local to this implementation (per the plan's own note to "bump a WAL format version byte") - a stream written under the old format now cleanly fails the magic check on its first record instead of being silently misparsed with the wrong field offsets.
  2. **`skipCorrupt` discarded everything after the first corrupt byte instead of skipping just the corrupt record**: on a bad magic value, `decodeRecords` did `if (skipCorrupt) break` - stopping the whole decode loop, not just that one record, so a single flipped byte anywhere in the segment silently dropped every record after it. The header-CRC and payload-CRC corrupt branches already skipped correctly (`offset = recordEnd; continue`) since a valid magic+length gives an exact record boundary to jump to - those just needed the counter added (next item).

  5. `kdb-storage-io`'s Native (`linuxX64`/`macosArm64`) target had two more real bugs, only reachable once (4) let `allTests` get this far: (a) `FileBackedPlatformIoShimFactory.native.kt`'s `open(config)` passed `config.rootDirectory` straight through to `NativeFileBackedPlatformIoShim`'s constructor, which `requireNotNull`s it - unlike the JVM factory, which generates a fallback temp directory (`java.io.tmpdir` + a unique suffix) when none is configured, so a caller relying on that same "just open one, I don't care where" convenience got an immediate crash on Native instead. **Fixed**: added the same fallback (`$TMPDIR-or-/tmp/kdb-data-<uuid>`) to the Native factory. (b) `NativeSegmentByteStore.append()` only writes into an in-memory `buffers` map - a real file only exists once `flush()`/`markSealed()` persists it - but `list()` only scanned the real filesystem, so a segment that had been appended-to but not yet flushed was invisible to `listSegments()`. This didn't affect JVM: `JvmSegmentByteStore.append()` writes straight through to a real `FileChannel`, so its filesystem-scan-based `list()` never needed to look anywhere else - the two stores' listing semantics had silently drifted apart purely from this buffering-timing difference. **Fixed**: `list()` now unions the filesystem scan with `buffers.keys`. Caught directly by the existing (already-written, never-before-run-on-this-target) `PlatformIoShimTest` in `commonTest` - no new test needed, `:kdb-storage-io:macosArm64Test` (8/8) and the rest of `:kdb-storage-io:allTests` went from 7 crashing + 1 failing to fully green.
